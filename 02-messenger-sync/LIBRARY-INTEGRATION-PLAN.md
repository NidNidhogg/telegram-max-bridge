# План внедрения библиотек Telegram ↔ MAX

Дата: 20.10.2026. Статус: **отложено; внедрение SDK не начато**.

После обсуждения пользы SDK принято сохранить текущие платформенные адаптеры. Следующая согласованная работа — [асинхронность на asyncio/aiohttp](ASYNC-IMPLEMENTATION-PLAN.md), затем webhook и серверный запуск. Ниже сохранён условный план на случай подтверждённой необходимости aiogram/maxapi; его этапы не являются обязательными для P1. Уже выполненную к тому моменту асинхронность и выделение транспорта повторять не нужно.

Цель: заменить обслуживание API готовыми библиотеками, сохранив проверенную логику доставки. Исходная точка — `1f31580`, SQLite schema 3, 51 тест и локальный `smoke_p0.py` по [протоколу P0](poc/P0-VALIDATION.md). Эти результаты относятся к текущему коду; совместная установка и работа новых SDK пока не проверены.

При возвращении к SDK пересмотреть состояние кода и пройти только оставшиеся этапы в порядке **L0 → L1 → L2 → L3 → L4 → L5 → L6**. Каждый этап заканчивается прогоном нового кода, тестами, обновлением документации и отдельным коммитом. При провале критериев следующий этап не начинаем.

## Выбранный набор

| Компонент | Назначение | Решение |
|---|---|---|
| `aiogram` | Клиент Telegram: методы API, отправка, файлы, типы ответов | Кандидат `3.31.0`; точную версию фиксируем после L0 |
| `maxapi` от `love-apples` | Клиент MAX: события, отправка, загрузка изображений, подписки | Кандидат `1.2.3`; это сторонняя библиотека |
| `aiohttp` | Асинхронный HTTP и один сервер с двумя webhook-маршрутами | Общая зависимость SDK; указываем как прямую, поскольку используем её сами |
| `asyncio`, `sqlite3`, `unittest` | Выполнение, устойчивая очередь, тесты | Стандартная библиотека Python 3.11+ |

По метаданным кандидатов диапазоны зависимостей пересекаются: `aiohttp >=3.13,<3.15`, `pydantic >=2.12,<2.14`. Это предварительная проверка совместимости, а не результат установки. Источники: [aiogram 3.31.0](https://github.com/aiogram/aiogram/blob/v3.31.0/pyproject.toml), [maxapi 1.2.3](https://github.com/love-apples/maxapi/blob/4771e78ee90c494f606cbb7507ad0e059b598922/pyproject.toml), [релиз maxapi](https://github.com/love-apples/maxapi/releases/tag/v1.2.3).

Для воспроизводимости используем один `pyproject.toml` и `uv.lock`; `uv` — инструмент установки, не часть работающего сервиса. Дополнительные хранилища, брокеры, веб-фреймворки и второй Telegram SDK в этот план не входят. Для async-тестов достаточно `unittest.IsolatedAsyncioTestCase`.

## Граница между нашим кодом и SDK

Наш код отвечает за выбор группы, нормализацию, подпись автора, разделение длинного текста, сопоставление ответов, SQLite, карантин, аудит, порядок доставки, лимиты отправки и решения `pending/sending/sent/failed/uncertain/skipped`. SDK отвечает за вызовы API, сериализацию запросов, multipart и разбор штатных ответов.

В текущем `poc/bridge.py` основные точки изменения — `Api`, `Bridge.poll()`, `Bridge.deliver()` и цикл `main()`. `Store` и операторские команды сохраняют свои контракты. На границе транспорта используем простые данные: исходное событие, подготовленное вложение, ID отправленного сообщения и контролируемая ошибка. Объекты SDK не сохраняем в SQLite.

Целевая схема:

```text
Webhook / тестовый polling
          ↓
проверка секрета и группы → исходный JSON → нормализация / карантин
          ↓
       SQLite commit → подтверждение приёма
          ↓
по одному отправителю на направление
          ↓
TelegramTransport (aiogram) / MaxTransport (maxapi)
          ↓
результат и reply-связь в SQLite
```

Два постоянных сетевых клиента с отдельными настройками TLS работают в одном event loop; HTTP-сессии закрываются при завершении. Транзакции SQLite короткие, без сетевых ожиданий внутри.

## L0. Проверить применимость SDK и зафиксировать зависимости

**Работа.** В отдельном окружении разрешить зависимости кандидатов; проверить Python 3.11 и выбранную серверную версию. Зафиксировать точные версии и lock-файл. Проверить доступность нужных методов, настройку `platform-api2.max.ru`, дополнительных сертификатов MAX, таймаутов, отключения retry и закрытия сессий. Подготовить синтетические ответы API и локальный HTTP-стенд; рабочие токены и базу не использовать.

Проверить возможности, которые могут изменить решение о библиотеке: получение исходного события до типизированного разбора, извлечение кода ошибки и `retry_after`, загрузка JPEG/PNG/WEBP, передача reply-ID. Изучить повторы не только SDK, но и используемого HTTP-клиента. Если требуются патчи приватных методов SDK или собственная копия библиотеки, остановить её внедрение и записать конкретный пробел.

**Проверка.** Чистая установка из lock-файла, проверка зависимостей, создание/закрытие обоих клиентов и вызовы через локальный стенд. Отдельно доказать, что одна попытка публикации не порождает скрытый повтор при 502/503/504 или разрыве соединения.

**Документация.** Создать `poc/LIBRARY-VALIDATION.md` с версиями, командами и фактическими результатами. Обновить инструкции окружения, отличая текущее приложение от среды миграции.

**Готово:** выбранные версии совместимы и позволяют сохранить наши правила доставки без форка SDK.

## L1. Выделить транспорт из рабочего ядра

**Работа.** Выделить небольшие адаптеры Telegram и MAX, пока использующие текущий HTTP-код. Перенести в них получение событий, подготовку вложений и публикацию; оставить переходы состояния задачи в ядре. Предусмотреть отдельную границу между подготовкой фото и запросом, который публикует сообщение.

Сохранить CLI, формат payload, ID, курсоры и схему 3. Не превращать это в полную переработку проекта: извлечь только модули, необходимые для замены транспорта.

**Проверка.** Полный текущий набор тестов и `smoke_p0.py`. Сравнить на синтетической базе очередь, reply-связи, карантин и результаты операторских команд до/после изменения. Проверить, что старые задачи читаются новым кодом.

**Документация.** Обновить `HOW-IT-WORKS.md` и протокол миграции.

**Готово:** бизнес-логика работает через адаптеры, поведение и база совместимы с исходной версией.

## L2. Перевести выполнение на asyncio

**Работа.** Реализовать один event loop: два получателя в режиме тестового polling, два последовательных отправителя и heartbeat. На переходном этапе синхронные сетевые операции старых адаптеров допустимо выполнять через `asyncio.to_thread`; доступ к `Store` туда не передавать. После L3–L4 эта временная обёртка удаляется.

SQLite остаётся под управлением одного потока с короткими транзакциями без `await`; получение задачи и фиксация `sending` выполняются атомарно. Сохраняются процессная блокировка и обслуживание очереди только при остановленном мосте. Ввести явные connect/read/total timeout и корректную остановку с ограниченным ожиданием активной отправки. Отмена запроса после начала публикации оставляет `uncertain` либо `sending`, которое восстановление переводит в `uncertain`.

**Проверка.** Зависший MAX не блокирует независимые операции Telegram; одна задача не захватывается дважды; порядок внутри направления сохраняется. Проверить SIGTERM и аварийное завершение до запроса, во время публикации и после ответа до записи результата. Повторить P0 и сквозной прогон, адаптировав тестовые API к async.

**Документация.** Описать выполнение и остановку в `HOW-IT-WORKS.md`/`OPERATIONS.md`, записать результаты.

**Готово:** выполнены критерии P1.1; поведение очереди сохраняется при конкурентных сетевых операциях.

## L3. Подключить aiogram для Telegram

**Работа.** Заменить Telegram-адаптер: проверка бота и чата, `sendMessage`, `sendPhoto`, `getFile` и загрузка файла. Сохранить текст без неожиданного parse mode, отключение предпросмотра ссылок, подпись автора и `reply_parameters`.

Тестовый polling обязан передавать исходные события в нашу обработку до строгой проверки SDK-моделями. Обычный типизированный `getUpdates` не принимаем без теста некорректного элемента пакета. Если публичный API aiogram не даёт нужный raw-результат, оставить узкий вызов `getUpdates` через уже выбранный `aiohttp`; это документированное исключение для тестового polling. Курсор продвигает только наша транзакция. Готовый polling-dispatcher не должен независимо подтверждать события.

Ошибки SDK преобразовать в наши контролируемые ошибки без токена, URL или тела ответа. Ошибка разбора ответа после возможной публикации означает `uncertain`. Сохранить предел фото 10 MiB, проверку фактического формата и ограниченное скачивание.

**Проверка.** Тексты, длинный Unicode, фото, подписи и ответы через реальный SDK на локальном стенде. 429 соблюдает задержку; 403 даёт определённый отказ; таймаут/5xx/неразбираемый ответ после публикации не вызывают повтор. Некорректное входное событие не теряется при типизации. Полная регрессия и сквозной запуск новой версии.

**Документация.** Обновить запуск, описание Telegram-адаптера и протокол проверки; явно отметить временно оставшийся старый MAX-адаптер.

**Готово:** Telegram использует aiogram, все прежние сценарии имеют тот же результат.

## L4. Подключить maxapi для MAX

**Работа.** Заменить MAX-адаптер: получение событий в тестовом режиме, проверка бота/чата, загрузка фото, отправка и reply-связь. `maxapi 1.2.3` предоставляет raw JSON через `get_updates`; передавать его в существующую обработку пакета, сохраняя атомарность задач, карантина и marker. Источник: [реализация GetUpdates](https://github.com/love-apples/maxapi/blob/4771e78ee90c494f606cbb7507ad0e059b598922/maxapi/methods/get_updates.py).

Встроенные повторы отключить через `DefaultConnectionProperties(max_retries=0)`: повтором управляет наша очередь. В исследованной версии по умолчанию установлено 3 повтора, включая 502/503/504, а механизм обработки ошибок соединения применяется к запросам API. Конфигурацию обязательно проверить по фактическому числу запросов на стенде. Источники: [настройки](https://github.com/love-apples/maxapi/blob/4771e78ee90c494f606cbb7507ad0e059b598922/maxapi/client/default.py), [реализация запросов](https://github.com/love-apples/maxapi/blob/4771e78ee90c494f606cbb7507ad0e059b598922/maxapi/connection/base.py).

Сохранить отдельный SSL context MAX, проверку доменов и перенаправлений медиа, отсутствие токена на файловых запросах. Загрузка вложения должна завершаться до отметки `sending`; отправка сообщения выполняется отдельным вызовом. Сохранить обработку `attachment.not.ready` как определённого отказа с отложенным повтором.

**Проверка.** Полная матрица текст/фото/ответы в обе стороны через два SDK; пакет «корректное → некорректное → корректное»; неизвестные поля события; дополнительные сертификаты и перенаправления. Сценарий «сервер принял сообщение, ответ потерян» даёт одну сетевую попытку и `uncertain`. Выполнить регрессию и сквозной прогон.

**Документация.** Обновить запуск, работу с TLS, правила повторов и протокол проверки.

**Готово:** обе платформы используют SDK; отправка не повторяется скрыто внутри библиотек.

## L5. Добавить webhook и соответствующую диагностику

**Работа.** Один `aiohttp`-сервер, два маршрута, секреты Telegram/MAX, ограничение тела запроса. Входной JSON сначала проходит проверку принадлежности выбранной группе и нашу обработку; задачи либо карантин фиксируются до `200 OK`. Дубликат можно подтвердить после проверки уже сохранённой записи; чужие чаты игнорируются без архивирования. Ошибка SQLite даёт неуспешный HTTP-ответ. Событие, для которого невозможно безопасно определить чат, не подтверждается как принятое.

Использовать явные короткие обработчики приёма; отправка выполняется только из SQLite-очереди. Типизация SDK или фоновая задача не должны оказаться единственным местом хранения события. Если используется `aiogram.SimpleRequestHandler`, параметр `handle_in_background=False` необходим, но сам по себе не гарантирует сохранение: commit обязан завершиться внутри пути обработки до ответа. [Документация aiogram](https://docs.aiogram.dev/en/latest/dispatcher/webhook.html).

Для `health` различать режимы получения событий: отсутствие новых webhook в тихой группе не является сбоем. Проверять heartbeat, доступность endpoint извне, состояние подписок, ошибки приёма и возраст очереди; время последнего события показывать отдельно.

Настроить HTTPS и подписки в рамках P1.2. Для MAX production требует webhook; polling остаётся режимом разработки/тестов. Источники: [режимы MAX](https://dev.max.ru/docs-api/use-cases/event-notifications), [подписка и секрет MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions), [секрет Telegram](https://core.telegram.org/bots/api#setwebhook).

**Проверка.** Неверный секрет, превышение размера, повтор события, некорректные данные выбранного чата, отказ диска, сбой до/после commit. Убить процесс после записи до HTTP-ответа: повтор webhook не создаёт вторую задачу. Проверить тихую группу без ложной тревоги и обнаружение недоступного endpoint. Локальная HTTP-проверка не заменяет проверку публичного HTTPS и подписок на сервере.

**Документация.** Обновить `SERVER-DEPLOYMENT-PLAN.md`, `HOW-IT-WORKS.md`, `OPERATIONS.md` и протокол.

**Готово:** выполнены критерии HTTP-приёма P1.2, тестовая серверная пара принимает события с подтверждением после записи.

## L6. Провести живую приёмку, переключить и удалить временный код

**Работа.** На отдельных тестовых ботах и группах выполнить матрицу приёмки: по 20 исходных сообщений в каждом направлении от нескольких участников, одинаковые тексты разных авторов, фото с подписью, ответы на оригинал и копию, длинный Unicode, перезапуск и пятиминутный простой. Неопределённую публикацию и аварии по точкам проверять на локальном стенде, где можно точно управлять сбоем.

Перед переключением существующей пары остановить прежний процесс, проверить очередь и `uncertain`, сделать согласованную копию SQLite. Перенести актуальную базу со связями ответов, проверить bot/chat identity, настроить подписки без удаления ожидающих обновлений. В каждый момент работает один экземпляр с этой парой ботов.

Удалить старый транспорт и временные `to_thread`-обёртки после успешной приёмки. Оставить один путь отправки на каждую платформу и необходимые ограничения скачивания медиа. Откат обеспечивается предыдущим коммитом и его окружением; постоянного выбора между двумя реализациями не добавляем.

**Проверка.** Чистая установка из lock-файла, все тесты, отдельный сквозной запуск, живая матрица, остановка/запуск и проверка очереди после переключения. Приёмка фиксирует число исходных и целевых сообщений, задержки, проблемы и наблюдаемые ограничения.

**Документация.** Итоговый протокол миграции, новая запись живого теста, актуальные README, инструкция оператора и общий план. Исторические результаты P0 не переписывать.

**Готово:** обе стороны работают через выбранные библиотеки, временный код удалён, переключение и откат проверены. Для постоянного пилота также нужны хранение/восстановление P1.3 и общесистемная приёмка P1.4.

## Общие правила проверки и отката

После каждого изменения кода: тесты соответствующего поведения → полный регрессионный набор → отдельный запуск нового кода на временной базе/локальном API → запись фактического результата в документацию → коммит. Для L3–L5 проверять SDK на уровне HTTP, а не только заменять вызов клиента заглушкой: иначе скрытые retry и ошибки типизации останутся незамеченными.

Отдельно различать чтение/подготовку вложения и публикацию. Определённый отказ 429 или `attachment.not.ready` допускает отложенный повтор; неоднозначный результат публикации требует `uncertain` и ручного разбора. Отсутствие дублей в штатном тесте не является гарантией exactly-once при любых сетевых сбоях.

Схему 3 и сериализацию задач сохранять до завершения замены SDK. Если изменение схемы всё же необходимо, вынести его в отдельный проверяемый шаг с миграцией и проверкой обратной совместимости. При откате кода использовать актуальное согласованное состояние: восстановление старого backup после новых отправок может привести к повторной публикации.

После перехода на webhook откат должен учитывать подписки: старый polling и webhook одновременно не запускаются. Возврат к polling допустим для тестового окружения; рабочему серверу нужен проверенный релиз с webhook.

## Связь с общим планом

- L0–L1 — подготовка внедрения; необходимое выделение модулей переносится из P2 сюда.
- L2 — реализация P1.1.
- L3–L4 — последовательная замена API-клиентов.
- L5 — часть P1.2: webhook, его диагностика и проверка серверной пары.
- L6 — приёмка библиотек и переключение; дополняет, но не закрывает автоматически P1.3–P1.4.

Ближайший согласованный шаг — **A0 плана асинхронности**. L0 выполняется только при возвращении к решению о внедрении SDK, с повторной проверкой актуальных версий и пользы замены.
