# Проверка изменений P0 — 20.10.2026

Исходная точка: коммит `4386721`, 20 проходящих тестов. Проверки разработки ниже выполнялись на временных базах и подменённых API, без публикации сообщений в живые группы и без изменения рабочей `.state`. После них отдельно выполнены живой запуск и ручная проверка пользователя; см. последний раздел и [протокол 20.10](LIVE-TEST-2026-10-20.md).

## P0.1 — карантин входных событий

Реализованы отдельная валидация полей, карантин выбранных групп, защита от повторов, повторная обработка сохранённого события и отображение проблем в статусе. Схема базы версии 1; перед миграцией старой базы создаётся согласованная резервная копия с правами 0600.

Проверки после изменения кода, до обновления документации:

- `python3 -m unittest discover -s 02-messenger-sync/poc -p 'test_*.py' -v`: **25 тестов, OK**.
- `python3 -m py_compile .../bridge.py .../test_bridge.py`: успешно.
- Отдельный прогон: пакет «корректное → картинка MAX без URL → корректное» принят дважды; получены две задачи, обе отправлены через подменённый API. После открытия базы заново сохранены курсор `123` и одна открытая проблема; `status` показывает её без текста сообщения.
- Регрессионные тесты проверяют откат задач, карантина и курсора при ошибке SQLite; неподавление программных ошибок; отсутствие архивирования чужого чата; восстановление карантина; миграцию без потери отправленных задач.

Ограничение: событие без определяемого чата не архивируется и не подтверждается. Повторная обработка после исправления обработчика может доставить сообщение позже новых сообщений. Живая инъекция некорректного события не выполнялась; последующая ручная проверка подтверждает общий обмен, а не каждый аварийный сценарий.

## P0.2 — управление очередью

Добавлены команды просмотра и разбора задач/карантина, состояние `skipped`, журнал `audit`, проверка ID найденной копии, обработка оставшихся частей сообщения. Изменения выполняются только при свободной блокировке процесса; просмотр использует read-only соединение. Схема базы версии 2; миграции сохраняют предварительную резервную копию.

Проверки после изменения кода, до обновления документации:

- Полный unittest-прогон: **36 тестов, OK**; проверка синтаксиса успешна.
- Отдельный прогон настоящего CLI через новые процессы на временной базе: подтверждение `uncertain`, повтор `failed`, пропуск трёх частей, повтор того же подтверждения и продолжение доставки через подменённый API.
- Итог: две отправленные задачи, три пропущенные части, пять записей аудита. Повтор подтверждения не добавил аудит или отправку.
- Автотесты проверяют запрет изменения `sending`, обязательное признание риска для повтора `uncertain`, уникальность ID копии, сохранение reply-связи и откат действия при ошибке записи аудита.
- Проверены запрет изменения при занятом `process.lock`, отсутствие сетевых вызовов в командах обслуживания и отсутствие текста переписки в выводе.

Ограничение: `confirm` фиксирует результат ручной сверки оператора и не проверяет существование копии сетевым запросом. Причины ручных решений хранятся в локальной таблице `audit`; в обычный вывод включены только метаданные действий.

## P0.3 — состояние и оповещения

Добавлены время создания/обновления задач, heartbeat и состояние процесса, время успешных опросов и доставок, расширенный статус, машинный `health` и отдельный монитор. Схема базы версии 3; у старых задач без временных полей возраст остаётся неизвестным. Монитор хранит наблюдения и очередь оповещений отдельно в `monitor.sqlite3`.

Проверки после изменения кода, до обновления документации:

- Полный unittest-прогон: **51 тест, OK**. Проверены пустая исправная очередь, сбой одного API и очистка ошибки после успешного опроса, остановка процесса при свежем heartbeat, устаревание опросов, возраст очереди и неизвестный возраст старых задач.
- Проверена миграция реальной старой структуры без временных колонок: задачи сохранены, предварительная копия содержит прежнюю схему.
- Монитор выдаёт одну проблему и одно восстановление; неизменная проблема не повторяется после перезапуска. При ошибке вывода событие остаётся в очереди с тем же `event_id`. Недоступная база не вызывает ложное восстановление ранее известных проблем.
- Скрипт `smoke_p0.py` повторяет P0.1 и P0.2, затем запускает отдельные процессы моста и непрерывного монитора с интервалом 0,2 секунды и полностью локальным API. Проверены `health` с кодом 0, синтетический сбой MAX, одно событие `problem`, перезапуск монитора без дубля, одно событие `recovery`, SIGTERM моста и событие `process_stopped`; после остановки `health` возвращает код 1.
- JSONL-файл оповещений создан с правами 0600. Метаданные health и оповещений не включают тексты сообщений, полные ошибки, токены или приватные URL.
- Проверка синтаксиса всех трёх Python-файлов и `git diff --check`: успешно.

Повторить проверки:

Границы результата: рабочая `.state` и живые группы этим прогоном не изменялись. Настоящие платформы подменены; P0 не считается повторной живой проверкой Telegram/MAX. Оповещения подготовлены в stdout/локальном JSONL; внешний адресат, доставка ему и постоянная служба мониторинга ещё не настроены. После аварии между выдачей события и отметкой о выдаче возможен повтор с тем же `event_id`; внешний обработчик должен учитывать этот ID.
