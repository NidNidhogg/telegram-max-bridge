# Проверка асинхронности — 20.10.2026

Работы выполняются по [плану A0–A5](../ASYNC-IMPLEMENTATION-PLAN.md). Исходный код: `1f31580`, SQLite schema 3. Итог: A0–A4 выполнены, код `96a928f` запущен на тестовой паре; A5 выполнен частично и остановлен по просьбе пользователя. Проверки разработки используют временные базы, синтетические токены и локальные API; живая проверка отмечается отдельно.

## A0 — исходная точка и окружение

- До изменений повторены **51 тест, OK**, и `smoke_p0.py`, все три сценария P0 проходят.
- Добавлены `pyproject.toml`, `uv.lock` и отдельная `.venv`; зафиксирован `aiohttp==3.14.5`. SDK Telegram/MAX не устанавливались.
- После добавления HTTP-стенда проходят **53 теста** на Python **3.14.0** и **3.11.15**. Проверены потеря ответа POST после прогрева соединения и HTTP 503: сервер видит одну попытку публикации.
- Код рабочего моста на этом этапе не изменён. Runtime ещё синхронный; установка зависимости сама по себе его не меняет.

Повторение из корня репозитория:

```sh
rtk proxy uv sync --locked
rtk proxy uv run --locked python -m unittest discover -s 02-messenger-sync/poc -p 'test_*.py'
rtk proxy uv run --locked python 02-messenger-sync/poc/smoke_p0.py
```

HTTP-тестам требуется разрешение на локальный listener. Для дополнительной проверки Python 3.11 можно использовать `uv run --isolated --python 3.11 --locked ...`.

## A1 — граница публикации и захват задачи

- Формирование запроса публикации выделено в чистую функцию `publication()`. Вложения по-прежнему готовятся до начала публикации.
- `Store.start_sending()` атомарно захватывает только готовую головную `pending`-задачу; повторный захват, обгон очереди и захват отложенной задачи отклоняются. Схема базы и payload не изменены.
- **54 теста, OK**; отдельный `smoke_p0.py` проходит карантин, CLI-восстановление, монитор и остановку процесса на новой версии.
- Runtime на этапе A1 синхронный.

## A2 — async HTTP-транспорт

- Добавлен `AsyncApi` на `aiohttp`: постоянные сессии, ограниченные пулы, явные timeout 5/20/25 секунд, раздельное TLS-доверие, потоковые пределы JSON/фото и проверяемые перенаправления скачивания. API и POST не перенаправляются автоматически; токен MAX не попадает в файловый upload.
- **62 теста, OK**. HTTP-стенд проверяет запросы и multipart, коды/задержку 429, `attachment.not.ready`, потерю ответа, 5xx, невалидный/большой JSON, MIME по сигнатуре, лимит фото, redirect, таймаут и явную отмену. Секреты из ответов/исключений в контролируемые ошибки не попадают.
- Отдельный `smoke_async.py`: удерживаем MAX-запрос, пока Telegram успешно отправляет; потерянный ответ публикации не повторяется; сессии закрываются. `smoke_p0.py` также проходит.
- Старый HTTP/runtime остаётся только до подключения async-цикла в A3; автоматического переключения после сетевой ошибки нет.

## A3 — независимый runtime и остановка

- Старый `urllib`-транспорт и последовательный цикл удалены. `Api` асинхронный; `doctor/discover/run` используют один event loop на команду. По два получателя/отправителя и heartbeat; SQLite schema 3 без изменений, ожидание блокировки записи ограничено 100 мс.
- Отмена публикации сохраняет `uncertain`, подготовка фото — `pending`; после запроса остановки подготовленное фото уже не начинает публикацию. Результат без корректного ID не считается `sent`. Полное завершение worker и HTTP-сессий предшествует освобождению process.lock.
- **76 тестов, OK**. На настоящем локальном HTTP проверены удержание каждого poller при работе другого, heartbeat, 429/401/409, потеря ответа, ошибка программы, ошибка commit результата, отмена до/во время публикации, перекрытие попыток и порядок 100 текстов в каждую сторону.
- Отдельный `smoke_p0.py` проходит. `smoke_async.py` запускает настоящий CLI в дочернем процессе с реальным HTTP-клиентом, переносит по 20 синтетических текстов в каждом направлении и проверяет SIGTERM/перезапуск без дублей. Только проверка identity подменена синтетическими ID; в этом стенде интервалы отправки обнулены, реальные лимиты API этим тестом не измеряются.
- На момент завершения A3 живой процесс ещё не переключался; последующие результаты приведены ниже.

## A4 — длительный отказ, TLS, фото и ограничения ресурсов

- **81 тест, OK**, на Python 3.14.0 и 3.11.15. Дополнительно проверены реальный TLS с временным собственным сертификатом (MAX доверяет дополнительному CA, Telegram — нет; неверное имя узла отклоняется), блокировка SQLite, фото с native reply в обе стороны и отсутствие транзакции при сетевых ожиданиях.
- Потоковое чтение ограничено; клиент запрашивает `Accept-Encoding: identity` и не распаковывает неожиданный gzip до проверки лимита. Проверен отказ такого ответа. SQLite при занятой записи завершает попытку примерно за 100 мс; пакет и курсор не фиксируются частично. Сбой базы останавливает runtime, а не вызывает сетевой повтор публикации.
- Длительный `smoke_async.py --outage-seconds 300` на runtime A3 (`3cf0a97`) выдержал **300 секунд HTTP 503 всех MAX-запросов**. Готовая отправка в Telegram завершилась, новые Telegram-события принимались, возраст heartbeat и успешного опроса Telegram проверялся каждую секунду и оставался менее 5 секунд. После восстановления MAX ошибка опроса очистилась; `uncertain` не повторилась, следующий MAX-job остался за ней. SIGTERM и повторный запуск не дали дублей.
- После финальных ограничений HTTP повторены весь набор тестов, короткий HTTP/CLI-прогон и P0-прогон. Измерение короткого стенда: первые 40 доставок **4,168 с**, пиковый RSS дочернего процесса **47,3 MiB** на данном macOS/Python. Интервалы отправки на стенде обнулены; это не оценка скорости реальных API или размер VPS.
- AST-проверка и проверка синтаксиса: сетевых `await` внутри SQLite-транзакций нет.
- Живой async `doctor` с отдельным временным каталогом состояния проверил обе личности ботов, группы, права, TLS и отсутствие webhook без чтения событий, публикации или изменения подписок. Существующий рабочий процесс при этом не останавливался.
- На момент завершения A4 переключение ещё предстояло; результат A5 приведён ниже.
