# Размещение моста Telegram ↔ MAX на новом сервере

Статус на 20.10.2026: **план, выбор сервера**. Пользователь подтвердил, что сервера и домена пока нет. Рассматриваем REG.RU / REG.Cloud, раздел **«VDS/VPS серверы»**; конфигурация, цена и заказ ещё не подтверждены, развёртывание не выполнялось. Отдельный домен на этапе выбора VPS не покупаем.

Главная цель пользователя: **мост работает круглосуточно, даже когда ноутбук выключен**. Для этого приложение, очередь и монитор переносятся на постоянно работающий сервер с автозапуском и восстановлением после сбоя. Ноутбук перестаёт быть необходимым только после проверки серверного экземпляра и остановки локального.

Текущий [локальный прототип](HOW-IT-WORKS.md) получает события опросом API и использует SQLite для очереди. Для рабочего размещения нужно изменить способ получения событий: по [документации MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions) Long Polling не подходит для production; предусмотрен Webhook. Telegram также [поддерживает webhook](https://core.telegram.org/bots/api#setwebhook).

Актуализация 20.10.2026: P0.1–P0.3 и async-код P1.1 реализованы — карантин, операторские команды, `health`, локальный монитор stdout/JSONL и независимые сетевые задачи. Async-версия работает на двух тестовых группах, пользователь подтвердил работу; дополнительный тест дал 44 доставки, [протокол](LIVE-ASYNC-TEST-2026-10-20.md). После оставшихся проверок A5 планируются серверный запуск P1.2 и хранение P1.3. Локальные фоновые процессы пока не являются системными службами.

Текущий runtime использует `asyncio` и зафиксированный `aiohttp`; сетевые границы, обработка сбоев и переключение описаны в [плане асинхронности](../ASYNC-IMPLEMENTATION-PLAN.md). Webhook пока не реализован: в P1.2 планируется один `aiohttp`-сервер с двумя маршрутами. Внедрение aiogram/maxapi отложено. При переходе `health` должен проверять доступность приёма и подписки; отсутствие новых сообщений само по себе не считается отказом webhook.

## Ближайшие шаги

1. В разделе «VDS/VPS серверы» выбрать обычный Linux VPS с Ubuntu LTS и публичным IPv4. Стартовый ориентир — 2 vCPU, 2 GiB RAM, SSD от 20 GiB, без платной панели управления. Перед заказом проверить итоговую стоимость, включённый диск/IP и доступность нужного образа; это ориентир нашего проекта, а не подтверждённый тариф REG.RU. Заказ и оплата ещё не выполнены.
2. После создания получить IP и настроить SSH-доступ по ключу. Проверить исходящие HTTPS-соединения с обоими API непосредственно с сервера, TLS и возможность постоянного запуска служб. Существующий локальный мост на этом этапе продолжает работать.
3. Определить постоянный публичный HTTPS-адрес для webhook, затем реализовать и проверить серверный приём событий. Порядок выбора адреса описан ниже; домен не является условием покупки или первичной настройки VPS.
4. Подготовить службы моста и монитора, резервные копии, внешний канал оповещений и порядок отката. Выполнить оставшиеся проверки A5 и серверные проверки на тестовой паре.
5. Переключить один экземпляр с сохранением базы и проверить работу при остановленном локальном мосте, а затем при выключенном ноутбуке. После выполнения критериев готовности переходить к ограниченному рабочему пилоту.

## Домен и работа без ноутбука

Для SSH и исходящих запросов текущего polling-моста достаточно IP сервера: технически тестовый мост можно перенести на VPS без домена. Такой промежуточный запуск сохраняет ограничения тестового polling MAX и сам по себе не завершает P1.2 или вывод в production. Он не требует отдельной реализации транспорта: используется тот же код и очередь. Это возможный промежуточный шаг, его запуск пока не выполнялся.

Для целевого webhook нужен постоянный публичный HTTPS-адрес с доверенным сертификатом, доступный MAX и Telegram. Покупать отдельный домен необязательно: если позднее появится существующий домен, можно выделить поддомен; другой вариант — постоянное имя от хостинга с подходящим сертификатом. Наличие такого имени у выбранного тарифа REG.RU **не подтверждено**, его нужно проверить до выбора этого варианта. Если подходящего адреса нет, потребуется зарегистрировать домен.

Работа MAX webhook напрямую по IP с сертификатом на IP **не подтверждена**. В документации MAX указано совпадение доменного имени URL с CN/SAN сертификата; поэтому URL с голым IP не считаем готовым решением для рабочего запуска. Собственный сайт и интерфейс для участников не нужны: адрес используется только для доставки событий в мост.

## Предлагаемая схема первого серверного варианта

```text
Telegram ──HTTPS webhook──┐
                          ├── домен:443 → HTTPS-сервер → проверка секрета → SQLite-очередь
MAX ───────HTTPS webhook──┘                                          │
                                                                    ▼
                                                        один процесс отправки
                                                          ↙          ↘
                                                    Telegram API    MAX API
```

Один небольшой Linux VPS, одно постоянное имя с HTTPS, один экземпляр моста с двумя независимыми последовательными отправителями. Обработчик webhook проверяет секрет и допустимость запроса, сохраняет событие в SQLite и только **после записи** возвращает успешный ответ. Отправка на другую площадку выполняется отдельно из устойчивой очереди. Существующие правила сопоставления ответов, пометки автора, исключения собственных сообщений и защиты от дублей сохраняются. При росте нагрузки или необходимости нескольких экземпляров очередь можно перенести в PostgreSQL; для первой пары групп это не обязательное предварительное условие.

Для MAX endpoint должен быть доступен по **HTTPS на порту 443**, с сертификатом доверенного УЦ, совпадающим доменным именем и полной цепочкой. MAX требует ответ `200 OK` не позднее 30 секунд; для подписки можно задать `secret`, который приходит в `X-Max-Bot-Api-Secret`. При неудаче MAX повторяет доставку, но после восьми часов без успешного ответа может снять подписку — её состояние нужно проверять и оповещать ответственного. [Официальные требования MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions). Для Telegram `setWebhook` поддерживает `secret_token` с заголовком `X-Telegram-Bot-Api-Secret-Token`; при webhook `getUpdates` одновременно не работает. [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).

## Что требуется подготовить

1. VPS с постоянным диском, публичным IPv4, доступностью HTTPS:443 и исходящими HTTPS-запросами к Telegram и MAX. Для webhook — постоянное DNS-имя, направленное на сервер, либо проверенный HTTPS-адрес хостинга с маршрутизацией к приложению. Стартовый ориентир для теста — 2 vCPU, 2 GiB RAM и 20 GiB SSD; это инженерная оценка, которую нужно проверить на фактической нагрузке, а не спецификация выбранного провайдера.
2. Доступ администратора по SSH-ключу для настройки ОС. Открыть 443; SSH ограничить ключами и, если возможно, доверенными адресами. Настроить автоматическое обновление TLS-сертификата и проверку продления. Токены ботов и секреты webhook передавать только через защищённый канал/хранилище, **не в чат и не в Git**.
3. Разработать и протестировать два HTTP-обработчика webhook; изменить текущий цикл polling на приём событий. Для каждого события — валидация, запись до `200`, дедупликация по ID и отдельная отправка из очереди. Сохранить текущую обработку неоднозначного результата отправки `uncertain` для ручного разбора.
4. Запускать приложение и имеющийся монитор как системные службы с автозапуском и перезапуском после сбоя. Использовать готовый `health` и события монитора для очереди/процесса; подключить внешний канал и получателя оповещений. Дополнить проверками действительности обеих webhook-подписок, срока сертификата и места на диске. Логи не должны содержать токены, тексты переписки и приватные URL вложений.
5. Делать резервные копии SQLite согласованным способом, шифровать и проверять восстановление. До переноса реальной переписки определить срок хранения текстов, ID, имён и медиа-ссылок, круг доступа, место размещения и порядок удаления данных. Текущий прототип автоматически данные не очищает.

## Переход с локального процесса

Ответ Telegram → MAX уже проверен локально; оба направления нужно заново воспроизвести на серверной тестовой конфигурации. Перед переключением остановить локальный процесс: **два экземпляра с одними ботами запускать нельзя**. Убедиться, что очередь опустела и нет `uncertain`; сделать согласованную резервную копию SQLite. Если нужны сохранённые связи для ответов на старые сообщения, перенести состояние базы на сервер; при запуске с пустой базой такие ответы смогут превратиться в текстовую цитату. Секреты настроить на сервере отдельно.

Затем поднять HTTPS endpoint и службу, зарегистрировать webhook Telegram и подписку MAX на тестовые группы. При смене режима не использовать `drop_pending_updates`: это намеренно удаляет ожидающие события Telegram. Проверить доставку, ответы, фото, повторную доставку одного webhook, отсутствие циклов и восстановление после перезагрузки. Только после этого отключать локальную тестовую схему окончательно. Откат — остановить серверный экземпляр и вернуть один согласованный способ получения событий, проверив очередь и подписки.

## Критерии готовности

- При остановленном локальном мосте и выключенном ноутбуке новые сообщения продолжают проходить через сервер; база и монитор находятся на VPS. Обновление и наблюдение за сервисом не требуют постоянного SSH-сеанса.
- Текст, фото с подписью и ответы проходят **в обе стороны** между выбранными тестовыми группами; каждое исходное сообщение создаёт одну копию.
- После перезапуска сервера очередь сохраняется, уже отправленное не дублируется, новые сообщения доставляются; ошибки `failed`/`uncertain` видны ответственному.
- Webhook-подписки, сертификат и резервное восстановление проверены. Доступ к серверу и токенам ограничен; согласованы срок хранения и правила работы с персональными данными.

Локальный async-мост запущен и базовый обмен подтверждён. Сейчас выбираем VPS на REG.RU / REG.Cloud; покупка сервера и выбор HTTPS-адреса остаются открытыми. Подготовка VPS может идти параллельно оставшимся проверкам A5. Рабочее переключение выполняется после серверных проверок P1.2 по [общему плану](../IMPLEMENTATION-PLAN.md). Перед реализацией webhook повторно проверить требования официальных API.
