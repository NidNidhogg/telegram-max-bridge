# План размещения моста Telegram ↔ MAX на сервере заказчика

Согласованное описание сервиса приведено в [README](../../README.md). Здесь перечислены ещё не выполненные работы для переноса с локального компьютера.

Статус на 21.10.2026: **план, проверка сервера заказчика**. Заказчик располагает собственным сервером; ОС, доступные ресурсы, сеть, HTTPS-адрес и доступ ещё не подтверждены. Подготовлены [описание моста и требования к размещению](CUSTOMER-SERVER-REQUIREMENTS.md). Приоритет — использовать имеющуюся инфраструктуру после проверки. Покупка VPS на REG.RU / REG.Cloud рассматривалась как запасной вариант; заказ и развёртывание не подтверждены. Отдельный домен пока не покупаем.

Главная цель пользователя: **мост работает круглосуточно, даже когда ноутбук выключен**. Сначала переносим текущую тестовую версию на сервер заказчика как постоянную службу; затем реализуем webhook для рабочего режима. Приложение работает рядом с сайтом на сервере, а не как файл в каталоге веб-страниц. Ноутбук перестаёт быть необходимым только после проверки серверного экземпляра и остановки локального.

Текущий [локальный прототип](HOW-IT-WORKS.md) получает события опросом API и использует SQLite для очереди. Для рабочего размещения нужно изменить способ получения событий: по [документации MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions) Long Polling не подходит для production; предусмотрен Webhook. Telegram также [поддерживает webhook](https://core.telegram.org/bots/api#setwebhook).

Актуализация 20.10.2026: карантин, операторские команды, `health`, локальный монитор stdout/JSONL и независимые сетевые задачи реализованы. Async-версия прошла живой тест на двух группах с 44 доставками; расширенная приёмка остаётся частичной. Локальные фоновые процессы пока не являются системными службами.

Текущий runtime использует `asyncio` и зафиксированный `aiohttp`. Webhook пока не реализован: запланирован один `aiohttp`-сервер с двумя маршрутами. Внедрение aiogram/maxapi отложено. При переходе `health` должен проверять доступность приёма и подписки; отсутствие новых сообщений само по себе не считается отказом webhook.

## Порядок работ

1. Передать администратору [требования к размещению](CUSTOMER-SERVER-REQUIREMENTS.md) и проверить соответствие сервера **этапу 1**: Linux, ресурсы, доступ, постоянные службы, исходящий HTTPS, TLS и сохранение данных. При отсутствии подходящего места рассмотреть отдельную VM или VPS.
2. Подготовить отдельную учётную запись, код из приватного репозитория, Python-зависимости и каталог состояния. Согласовать защищённую передачу `.env` и при необходимости сертификата MAX; токены не передавать через Git. Пока идёт подготовка, локальный мост продолжает работать.
3. Сверить очередь и ошибки `uncertain`, остановить локальный мост и монитор, сделать согласованную копию SQLite, перенести `.state/bridge.sqlite3` и секреты. Запустить на сервере **один** экземпляр текущего polling-моста и отдельный монитор как службы. Проверить `doctor`, `health`, восстановление после перезапуска и доставку в обе стороны при выключенном ноутбуке. Если связь ответов со старыми сообщениями не нужна, можно начинать с новой базы только после осознанного решения владельца.
4. После тестового переноса проверить соответствие **этапу 2**: постоянный публичный HTTPS-адрес, сертификат и маршруты. Реализовать webhook, проверку секретов и устойчивую запись до подтверждения; подключить внешний канал оповещений, резервное копирование и правила хранения.
5. Проверить webhook на тестовой паре, оставшиеся сценарии живой приёмки, переключение и откат. К ограниченному рабочему пилоту переходить только после выполнения критериев готовности ниже.

## Домен и работа без ноутбука

Для SSH и исходящих запросов текущего polling-моста достаточно доступа сервера в сеть: тестовый мост можно перенести без домена и входящего порта. Такой промежуточный запуск сохраняет ограничения polling MAX и не является рабочим размещением. Используется тот же код и очередь; перенос пока не выполнялся.

Для целевого webhook нужен постоянный публичный HTTPS-адрес с доверенным сертификатом, доступный MAX и Telegram. Отдельный поддомен и покупка нового домена необязательны: можно выделить два пути на существующем домене заказчика, например `https://example.ru/bridge/telegram` и `https://example.ru/bridge/max`, и направить их через reverse proxy к приложению. Поддомен — другой допустимый вариант. Также можно использовать постоянное имя от хостинга с подходящим сертификатом; наличие такого имени у рассматривавшегося тарифа REG.RU **не подтверждено**. Если подходящего адреса нет, потребуется обеспечить его отдельно.

Работа MAX webhook напрямую по IP с сертификатом на IP **не подтверждена**. В документации MAX указано совпадение доменного имени URL с CN/SAN сертификата; поэтому URL с голым IP не считаем готовым решением для рабочего запуска. Собственный сайт и интерфейс для участников не нужны: адрес используется только для доставки событий в мост.

## Предлагаемая схема первого серверного варианта

```text
Telegram ──HTTPS webhook──┐
                          ├── домен:443 → HTTPS-сервер → проверка секрета → SQLite-очередь
MAX ───────HTTPS webhook──┘                                          │
                                                                    ▼
                                                      два отправителя в одном процессе
                                                          ↙          ↘
                                                    Telegram API    MAX API
```

Один Linux-сервер или VM, одно постоянное имя с HTTPS, один экземпляр моста с двумя независимыми последовательными отправителями. Обработчик webhook проверяет секрет и допустимость запроса, сохраняет событие в SQLite и только **после записи** возвращает успешный ответ. Отправка на другую площадку выполняется отдельно из устойчивой очереди. Существующие правила сопоставления ответов, пометки автора, исключения собственных сообщений и защиты от дублей сохраняются. При росте нагрузки или необходимости нескольких экземпляров очередь можно перенести в PostgreSQL; для первой пары групп это не обязательное предварительное условие.

Для MAX endpoint должен быть доступен по **HTTPS на порту 443**, с сертификатом доверенного УЦ, совпадающим доменным именем и полной цепочкой. MAX требует ответ `200 OK` не позднее 30 секунд; для подписки можно задать `secret`, который приходит в `X-Max-Bot-Api-Secret`. При неудаче MAX повторяет доставку, но после восьми часов без успешного ответа может снять подписку — её состояние нужно проверять и оповещать ответственного. [Официальные требования MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions). Для Telegram `setWebhook` поддерживает `secret_token` с заголовком `X-Telegram-Bot-Api-Secret-Token`; при webhook `getUpdates` одновременно не работает. [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).

## Что требуется подготовить для webhook и рабочего режима

1. Linux-сервер или VM с постоянным локальным диском, публичным HTTPS-входом на порту 443 и исходящими HTTPS-запросами к Telegram и MAX. Для webhook — постоянное DNS-имя с доверенным сертификатом и маршрутизацией к приложению. Существующий reverse proxy может принимать HTTPS:443 и передавать запросы внутреннему приложению; отдельный публичный IP для VM тогда не требуется. Стартовый ориентир для теста — 2 vCPU, 2 GiB RAM и 20 GiB SSD; это инженерная оценка, которую нужно проверить на фактической нагрузке.
2. Доступ администратора по SSH-ключу для настройки ОС. Открыть 443; SSH ограничить ключами и, если возможно, доверенными адресами. Настроить автоматическое обновление TLS-сертификата и проверку продления. Токены ботов и секреты webhook передавать только через защищённый канал/хранилище, **не в чат и не в Git**.
3. Разработать и протестировать два HTTP-обработчика webhook; изменить текущий цикл polling на приём событий. Для каждого события — валидация, запись до `200`, дедупликация по ID и отдельная отправка из очереди. Сохранить текущую обработку неоднозначного результата отправки `uncertain` для ручного разбора.
4. Запускать приложение и имеющийся монитор как системные службы с автозапуском и перезапуском после сбоя. Использовать готовый `health` и события монитора для очереди/процесса; подключить внешний канал и получателя оповещений. Дополнить проверками действительности обеих webhook-подписок, срока сертификата и места на диске. Логи не должны содержать токены, тексты переписки и приватные URL вложений.
5. Делать резервные копии SQLite согласованным способом, шифровать и проверять восстановление. До переноса реальной переписки определить срок хранения текстов, ID, имён и медиа-ссылок, круг доступа, место размещения и порядок удаления данных. Текущий прототип автоматически данные не очищает.

## Переключение и откат

Перед **первым переносом на сервер** остановить локальный процесс: **два экземпляра с одними ботами запускать нельзя**. Убедиться, что очередь опустела и нет `uncertain`; сделать согласованную резервную копию SQLite и перенести базу вместе с настройками. При запуске с пустой базой ответы на старые сообщения могут превратиться в текстовую цитату. Перенос `bridge.sqlite3` после остановки исключает расхождение с продолжающим запись локальным процессом; `MAX_CA_FILE` на сервере должен указывать на существующий доверенный сертификат, если он нужен.

Для **перехода с серверного polling на webhook** поднять HTTPS endpoint и службу, зарегистрировать webhook Telegram и подписку MAX на тестовые группы. При смене режима не использовать `drop_pending_updates`: это намеренно удаляет ожидающие события Telegram. Проверить доставку, ответы, фото, повторную доставку одного webhook, отсутствие циклов и восстановление после перезагрузки. Откат — остановить активный экземпляр и вернуть один согласованный способ получения событий, проверив очередь, базу и подписки.

## Критерии готовности

- При остановленном локальном мосте и выключенном ноутбуке новые сообщения продолжают проходить через сервер; база и монитор находятся на сервере заказчика или выбранной VM. Обновление и наблюдение за сервисом не требуют постоянного SSH-сеанса.
- Текст, фото с подписью и ответы проходят **в обе стороны** между выбранными тестовыми группами; каждое исходное сообщение создаёт одну копию.
- После перезапуска сервера очередь сохраняется, уже отправленное не дублируется, новые сообщения доставляются; ошибки `failed`/`uncertain` видны ответственному.
- Webhook-подписки, сертификат и резервное восстановление проверены. Доступ к серверу и токенам ограничен; согласованы срок хранения и правила работы с персональными данными.

Рабочее переключение выполняется после разработки и проверки серверного приёма. Требования HTTPS и webhook сверены 21.10.2026; перед переключением проверить их повторно и подтвердить фактическую доступность endpoint.
