# План доработки и размещения моста Telegram ↔ MAX

Согласованное описание сервиса приведено в [README](../../README.md). Здесь перечислены запланированные доработки и порядок размещения на одном сервере заказчика. Обновление плана не означает начало реализации.

Статус на 26.10.2026: **согласование плана доработки**. Разработчик заказчика получил доступ к репозиторию, посмотрел код и предложил развернуть сервис на существующем сервере с 1–2 ГБ диска под приложение. Это стартовый объём для проверки, а не подтверждённый предел длительного хранения. ОС, лимиты CPU/RAM, сеть, HTTPS-адрес и доступ ещё не подтверждены. Требования к площадке приведены в [отдельном документе](CUSTOMER-SERVER-REQUIREMENTS.md).

Главная цель пользователя: **мост работает круглосуточно, даже когда ноутбук выключен**. Сначала переносим текущую тестовую версию на сервер заказчика как постоянную службу; затем реализуем webhook для рабочего режима. Приложение работает рядом с сайтом на сервере, а не как файл в каталоге веб-страниц. Ноутбук перестаёт быть необходимым только после проверки серверного экземпляра и остановки локального.

Текущий [локальный прототип](HOW-IT-WORKS.md) получает события опросом API и использует SQLite для очереди. Для рабочего размещения нужно изменить способ получения событий: по [документации MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions) Long Polling не подходит для production; предусмотрен Webhook. Telegram также [поддерживает webhook](https://core.telegram.org/bots/api#setwebhook).

Актуализация 20.10.2026: карантин, операторские команды, `health`, локальный монитор stdout/JSONL и независимые сетевые задачи реализованы. Async-версия прошла живой тест на двух группах с 44 доставками; расширенная приёмка остаётся частичной. Локальные фоновые процессы пока не являются системными службами.

Текущий runtime использует `asyncio` и зафиксированный `aiohttp`. Webhook пока не реализован: запланирован один `aiohttp`-сервер с двумя маршрутами. Внедрение aiogram/maxapi отложено. При переходе `health` должен проверять доступность приёма и подписки; отсутствие новых сообщений само по себе не считается отказом webhook.

## Первая задача для Devin: D1 — контейнеризация одной связки

Подготовлено 28.10.2026. Статус: **задание подготовлено, в Devin ещё не отправлено**. Это самостоятельный первый PR для существующей одной пары групп Telegram ↔ MAX. Расширение на каналы и несколько связок, webhook и полная готовность к production остаются следующими задачами. Polling в результате D1 предназначен для тестирования на сервере.

Все изменения и исправления отправляются только в эту ветку. `main` используется как база сравнения и целевая ветка PR; прямые коммиты и push в `main`, force push, удаление веток и автоматическое слияние Devin запрещены. Если рабочая ветка уже существует, сначала проверить её принадлежность задаче D1 и продолжить без перезаписи истории.

- Код: `02-messenger-sync/poc/bridge.py`; тесты: `test_bridge.py`, `test_async.py`; сквозные стенды: `smoke_p0.py`, `smoke_async.py`. Зависимости зафиксированы в корневых `pyproject.toml` и `uv.lock`.

### Цель и границы изменений

Команда заказчика должна собирать, запускать и проверять текущий мост через Docker Compose и Makefile, без установки окружения Python на сервере. D1 включает Dockerfile, compose.yaml, Makefile, `.dockerignore`, поддержку конфигурации контейнера, необходимые проверки и актуализацию затронутых документов.

Допускаются небольшие изменения кода для чтения конфигурации и запуска в контейнере. Сохраняются одна пара групп, текущие тексты/фото/reply, схема базы, порядок очереди и правила `uncertain`. Новую политику автоматического повтора неопределённых публикаций, очистку данных, поддержку каналов и смену стека в этот PR не включать. Если упаковка обнаружит ошибку вне этих границ, описать её отдельно.

### Что реализовать

1. **Образ.** Установить зависимости из зафиксированного окружения. Приложение работает без root; в образ и контекст сборки не попадают `.env`, `.state`, рабочие базы, резервные копии, логи и локальная `.venv`. Учесть HTTPS-сертификаты. Не включать рабочие токены или машинные пути разработчика в образ и примеры.
2. **Конфигурация.** Поддержать передачу параметров через переменные окружения контейнера; `.env` допускается как закрытый источник этих переменных для Compose. Переменные окружения имеют приоритет перед значениями файла; пустой обязательный параметр вызывает понятную ошибку без вывода значения. Сохранить совместимость существующих проверок. Документировать параметры ботов, чатов, состояния и при необходимости путь к дополнительному сертификату MAX внутри контейнера. Файловые Docker secrets не обязательны для D1: вариант с переменными окружения соответствует требованию заказчика.
3. **Compose.** Запускать мост и существующий монитор отдельными сервисами с общим постоянным volume состояния. Сохранять весь каталог состояния, включая необходимые SQLite-файлы и данные монитора. Обеспечить запись для пользователя контейнера, перезапуск после выхода процесса и передачу SIGTERM приложению. Дать приложению завершить активные операции: таймаут остановки контейнера должен превышать текущие 30 секунд graceful shutdown. Для polling не публиковать порты на хосте, не требовать privileged-режима или доступа к Docker socket из контейнеров.
4. **Makefile.** Предоставить документированные рабочие цели `make build`, `make up`, `make down`, `make update`, `make logs`, `make status`, `make health`, `make test`, `make smoke`. Команды управления используют Compose; тесты и стенды выполняются в контейнере. Все изменяющие состояние действия относятся только к выбранному окружению проекта. Остановка и обновление не удаляют volume. Неудачная сборка обновления не должна предварительно останавливать рабочую версию. Запрещены фиктивно успешные заглушки команд.
5. **Healthcheck.** Использовать существующий `health --json` с корректным каталогом состояния и кодом завершения. Пустая исправная очередь допустима; блокирующая ошибка или устаревший heartbeat должны быть видны как проблема. Проверка не публикует сообщения. Показать это в статусе контейнера; не заявлять, что один healthcheck уже обеспечивает внешние оповещения или восстановление при любом зависании.
6. **Проверки и документация.** Выполнить существующие тесты, добавить проверки чтения настроек и отдельный контейнерный прогон. В README описать предпосылки Docker/Compose/Make, настройку одной пары ботов, команды, назначение volume, диагностику и ограничения тестового polling. Затронутые инструкции согласовать с интерфейсом `make`; работающие возможности и будущие требования описывать отдельно.

### Формат результата и независимая проверка

Devin работает в `codex/d1-docker-packaging` и открывает draft PR из этой ветки в `main` без автоматического слияния и без развёртывания на сервере заказчика. Devin самостоятельно не сливает PR; включение изменений в `main` выполняется после независимой проверки отдельным действием владельца репозитория. PR содержит краткое описание, соответствие D1-AC-01…D1-AC-09, точные команды и результаты, ограничения и список незавершённых проверок. Рабочие боты, существующая `.state` и токены разработчика или заказчика для реализации не используются: стенды и тестовые данные изолированы.

После получения PR проверяющий фиксирует SHA его вершины, изучает diff и тесты, затем независимо выполняет проверки этой версии в доступном Docker-окружении. Замечания возвращаются Devin как воспроизводимые сценарии с ожидаемым и фактическим результатом. После исправления проверяются затронутые сценарии и регрессия. Реальный обмен на выбранной паре тестовых групп и серверная приёмка идут отдельным согласованным прогоном; их нельзя подменять стендом или автоматически включать при просмотре PR.

Для передачи нужны доступ Devin к репозиторию и наличие этих документов в доступном ему коммите либо их передача вместе с заданием; это проверяется перед стартом. Прямой интеграции с Devin в текущей сессии нет: пользователь запускает задачу, а результат передаётся ссылкой на PR. Никакие действия в Devin этим документом не запускаются.

## Объём доработки

Заказчик указал **три канала и пять групп**, из которых один чат активный, остальные почти без активности. Для планирования принимаем до восьми пар Telegram ↔ MAX; окончательный список обеих сторон каждой пары нужно сверить. Проверка 30–40 связок не является условием приёмки этого объёма.

Три проекта: подбор и поставка оборудования — Oispro; компоненты косметики — Аромареалити; обучение технологов — Аромакраса. Группы курсов, включая «Гидролаты» и «ББ-кремы», привязываются к соответствующему проекту при составлении списка связок.

Целевое поведение каждой подключённой пары: Telegram и MAX — равноправные источники, новое сообщение или публикация с любой площадки появляются на другой без переключения настроек. Двусторонний обмен между одной парой групп уже работает. Задача — **добавить поддержку каналов в существующий двусторонний мост** и несколько независимых связок. Поддержка каналов и работа с несколькими связками ещё не реализованы. В текущем коде канал нельзя подключить простой заменой ID: получатель Telegram запрашивает только `message`, а `doctor` отклоняет каналы. Технические отличия описаны в [HOW-IT-WORKS.md](HOW-IT-WORKS.md#запланированное-добавление-каналов).

Объём этого плана: новые тексты, фотографии с подписями, ответы в группах и публикации в каналах. Комментарии под постами, видео, документы, импорт истории, синхронизация правок и удалений оцениваются отдельно. Считаем тематические группы отдельными чатами; темы внутри одной Telegram-группы требуют отдельного решения по маршрутизации.

## План доработок

1. **Зафиксировать список связок и исходное состояние.** Для каждой пары указать проект, ID Telegram и MAX, тип «группа» или «канал», ботов и права. Сделать согласованную копию текущей базы и воспроизвести существующие проверки. На первом этапе каждая площадка чата относится только к одной паре.
2. **Добавить конфигурацию нескольких связок и миграцию базы.** Ввести устойчивый ID связки, целевой чат в задаче и привязку к проекту. Перенести текущую пару, очередь, курсоры, карантин и связи ответов без повторной отправки. Изменение настроек не должно перенаправлять уже принятые задачи в другой чат.
3. **Разделить маршрутизацию и очереди по целевым чатам.** Сохранить общий приём событий каждого бота, распределять события по настроенным связкам, фиксировать курсор вместе со всеми принятыми задачами. Порядок сохранять внутри целевого чата; отправки между чатами распределять с учётом общих лимитов API и локальных лимитов чата. Ответы и защита от дублей должны учитывать связку, площадку и ID чата. `uncertain` блокирует только соответствующее направление связки и не повторяется автоматически.
4. **Добавить поддержку каналов в существующий двусторонний мост.** Принимать Telegram `channel_post` и публикации MAX, дополнить проверку типа чата и прав ботов. Использовать готовые механизмы подготовки текста, фото, очереди и доставки. Обработать публикации от имени канала и защиту от возврата собственных копий, в том числе при одновременной работе обеих площадок. На каждой стороне пользователь может создавать новые публикации без смены режима. Личного автора указывать только по доступным сведениям API; иначе обозначать исходный канал и площадку.
5. **Реализовать серверный приём через webhook.** Добавить маршруты Telegram и MAX в существующий `aiohttp`-процесс, проверку секретов, допустимых чатов, структуры и размера запроса. Подтверждать событие после устойчивой записи; повтор webhook не должен создавать вторую доставку. Использовать общую маршрутизацию и очередь для всех связок, ограничить параллельную обработку и загрузку медиа.
6. **Дополнить эксплуатацию.** Показывать статус, длину и возраст очереди, ошибки и последние доставки по проекту и связке. Добавить приостановку и возобновление отдельных связок с сохранением очереди, выбор связки в операторских командах, контроль прав ботов и подписок, оповещения о проблемах и восстановлении. Настроить ротацию журналов, контроль диска, сроки хранения и безопасную очистку; нерешённые задачи автоматически не удалять. Сроки хранения содержимого, связей ответов и записей защиты от дублей согласовать отдельно. Проверить резервное восстановление. Правила ручной сверки канальных копий и будущие действия оператора приведены в [OPERATIONS.md](OPERATIONS.md#запланированная-эксплуатация-каналов-и-нескольких-связок).
7. **Проверить восемь связок и сбои.** Проверить текст, фото и ответы в группах, публикации в каналах с обеих сторон, одинаковые ID сообщений в разных чатах и отсутствие обмена между чужими парами. Для каналов отдельно проверить публикацию от имени канала, два самостоятельных поста с одинаковым текстом, повторное событие о копии и его приход до сохранения результата отправки; обрыв ответа API не должен вызывать цикл или автоматический повтор неопределённой публикации. Воспроизвести один активный чат при семи тихих, блокировку одной очереди, ограничения API, пятиминутный отказ площадки и перезапуск с ожидающими задачами. Измерить задержки, рост базы, память и сеть на согласованном потоке; проверить восстановление из резервной копии и нехватку места.
8. **Разместить и провести приёмку.** Подготовить службы моста и монитора на сервере заказчика, TLS, резервные копии, внешние оповещения и порядок обновления. Подключать связки последовательно после проверки одной группы и одного канала. Остановить локальный экземпляр перед переключением тех же ботов; проверить работу при выключенном ноутбуке и после перезагрузки сервера.

После каждого изменения кода: подходящие автоматические тесты → отдельный сквозной прогон нового кода → обновление существующей документации. Живые проверки выполняются в явно выбранных тестовых чатах и каналах; рабочие связки подключаются после приёмки. Код и документы разделяют реализованное поведение и запланированные возможности.

Предварительный ориентир — около десяти рабочих дней одного разработчика при готовых доступах и перечисленном объёме; ожидание доступов, согласования и дополнительные типы содержимого в оценку не входят.

## Порядок размещения

1. Передать администратору [требования к размещению](CUSTOMER-SERVER-REQUIREMENTS.md) и проверить соответствие сервера **этапу 1**: Linux, ресурсы, доступ, постоянные службы, исходящий HTTPS, TLS и сохранение данных. При отсутствии подходящего места рассмотреть отдельную VM или VPS.
2. Подготовить отдельную учётную запись, код из приватного репозитория, Python-зависимости и каталог состояния. Согласовать защищённую передачу `.env` и при необходимости сертификата MAX; токены не передавать через Git. Пока идёт подготовка, локальный мост продолжает работать.
3. Сверить очередь и ошибки `uncertain`, остановить локальный мост и монитор, сделать согласованную копию SQLite, перенести `.state/bridge.sqlite3` и секреты. Запустить на сервере **один** экземпляр текущего polling-моста и отдельный монитор как службы. Проверить `doctor`, `health`, восстановление после перезапуска и доставку в обе стороны при выключенном ноутбуке. Если связь ответов со старыми сообщениями не нужна, можно начинать с новой базы только после осознанного решения владельца.
4. После тестового переноса проверить соответствие **этапу 2**: постоянный публичный HTTPS-адрес, сертификат и маршруты. Реализовать webhook, проверку секретов и устойчивую запись до подтверждения; подключить внешний канал оповещений, резервное копирование и правила хранения.
5. Проверить webhook сначала на тестовой паре групп и тестовой паре каналов, затем на всех согласованных связках. Проверить оставшиеся сценарии живой приёмки, переключение и откат. К ограниченному рабочему пилоту переходить только после выполнения критериев готовности ниже.

## Домен и работа без ноутбука

Для SSH и исходящих запросов текущего polling-моста достаточно доступа сервера в сеть: тестовый мост можно перенести без домена и входящего порта. Такой промежуточный запуск сохраняет ограничения polling MAX и не является рабочим размещением. Используется тот же код и очередь; перенос пока не выполнялся.

Для целевого webhook нужен постоянный публичный HTTPS-адрес с доверенным сертификатом, доступный MAX и Telegram. Отдельный поддомен и покупка нового домена необязательны: можно выделить два пути на существующем домене заказчика, например `https://example.ru/bridge/telegram` и `https://example.ru/bridge/max`, и направить их через reverse proxy к приложению. Поддомен — другой допустимый вариант. Также можно использовать постоянное имя от хостинга с подходящим сертификатом; наличие такого имени у рассматривавшегося тарифа REG.RU **не подтверждено**. Если подходящего адреса нет, потребуется обеспечить его отдельно.

Работа MAX webhook напрямую по IP с сертификатом на IP **не подтверждена**. В документации MAX указано совпадение доменного имени URL с CN/SAN сертификата; поэтому URL с голым IP не считаем готовым решением для рабочего запуска. Собственный сайт и интерфейс для участников не нужны: адрес используется только для доставки событий в мост.

## Предлагаемая схема первого серверного варианта

```text
Telegram ──HTTPS webhook──┐
                          ├── домен:443 → HTTPS-сервер → проверка секрета → SQLite-очередь
MAX ───────HTTPS webhook──┘                                          │
                                                                    ▼
                                                      планировщик отправок по чатам
                                                          ↙          ↘
                                                    Telegram API    MAX API
```

Один Linux-сервер или VM, одно постоянное имя с HTTPS, один экземпляр моста с независимыми очередями целевых чатов и ограниченной параллельной отправкой. Обработчик webhook проверяет секрет и допустимость запроса, сохраняет событие в SQLite и только **после записи** возвращает успешный ответ. Отправка на другую площадку выполняется отдельно из устойчивой очереди с общими ограничениями каждой платформы. Существующие правила сопоставления ответов, пометки автора, исключения собственных сообщений и защиты от дублей расширяются на несколько связок. SQLite сохраняется до появления подтверждённой потребности в другом хранилище.

Для MAX endpoint должен быть доступен по **HTTPS на порту 443**, с сертификатом доверенного УЦ, совпадающим доменным именем и полной цепочкой. MAX требует ответ `200 OK` не позднее 30 секунд; для подписки можно задать `secret`, который приходит в `X-Max-Bot-Api-Secret`. При неудаче MAX повторяет доставку, но после восьми часов без успешного ответа может снять подписку — её состояние нужно проверять и оповещать ответственного. [Официальные требования MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions). Для Telegram `setWebhook` поддерживает `secret_token` с заголовком `X-Telegram-Bot-Api-Secret-Token`; при webhook `getUpdates` одновременно не работает. [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).

## Что требуется подготовить для webhook и рабочего режима

1. Linux-сервер или VM с постоянным локальным диском, публичным HTTPS-входом на порту 443 и исходящими HTTPS-запросами к Telegram и MAX. Для webhook — постоянное DNS-имя с доверенным сертификатом и маршрутизацией к приложению. Существующий reverse proxy может принимать HTTPS:443 и передавать запросы внутреннему приложению; отдельный публичный IP для VM тогда не требуется. Заказчик предложил 1–2 ГБ под приложение; проверить размер окружения, базы и журналов, согласовать лимиты CPU/RAM и контролировать рост данных с учётом работы Битрикс на том же сервере.
2. Доступ администратора по SSH-ключу для настройки ОС. Открыть 443; SSH ограничить ключами и, если возможно, доверенными адресами. Настроить автоматическое обновление TLS-сертификата и проверку продления. Токены ботов и секреты webhook передавать только через защищённый канал/хранилище, **не в чат и не в Git**.
3. Разработать и протестировать два HTTP-обработчика webhook; изменить текущий цикл polling на приём событий. Для каждого события — валидация, запись до `200`, дедупликация по ID и отдельная отправка из очереди. Сохранить текущую обработку неоднозначного результата отправки `uncertain` для ручного разбора.
4. Запускать приложение и имеющийся монитор как системные службы с автозапуском и перезапуском после сбоя. Использовать готовый `health` и события монитора для очереди/процесса; подключить внешний канал и получателя оповещений. Дополнить проверками действительности обеих webhook-подписок, срока сертификата и места на диске. Логи не должны содержать токены, тексты переписки и приватные URL вложений.
5. Делать резервные копии SQLite согласованным способом, шифровать и проверять восстановление. До переноса реальной переписки определить срок хранения текстов, ID, имён и медиа-ссылок, круг доступа, место размещения и порядок удаления данных. Текущий прототип автоматически данные не очищает.

## Переключение и откат

Перед **первым переносом на сервер** остановить локальный процесс: **два экземпляра с одними ботами запускать нельзя**. Убедиться, что очередь опустела и нет `uncertain`; сделать согласованную резервную копию SQLite и перенести базу вместе с настройками. При запуске с пустой базой ответы на старые сообщения могут превратиться в текстовую цитату. Перенос `bridge.sqlite3` после остановки исключает расхождение с продолжающим запись локальным процессом; `MAX_CA_FILE` на сервере должен указывать на существующий доверенный сертификат, если он нужен.

Для **перехода с серверного polling на webhook** поднять HTTPS endpoint и службу, зарегистрировать webhook Telegram и подписку MAX на тестовые группы. При смене режима не использовать `drop_pending_updates`: это намеренно удаляет ожидающие события Telegram. Проверить доставку, ответы, фото, повторную доставку одного webhook, отсутствие циклов и восстановление после перезагрузки. Откат — остановить активный экземпляр и вернуть один согласованный способ получения событий, проверив очередь, базу и подписки.

## Критерии готовности

- При остановленном локальном мосте и выключенном ноутбуке новые сообщения продолжают проходить через сервер; база и монитор находятся на сервере заказчика или выбранной VM. Обновление и наблюдение за сервисом не требуют постоянного SSH-сеанса.
- На всех согласованных связках новые тексты и фото с подписями проходят **в обе стороны**; ответы в группах связаны с правильными сообщениями, канальные публикации можно создавать на любой площадке. Каждый принятый исходный пост создаёт одну доставку в парную площадку, без возврата по кругу и попадания в другие связки; длинный пост может разбиваться на несколько частей по текущим правилам. Комментарии под канальными постами в эту приёмку не входят.
- Активный чат или `failed`/`uncertain` одной связки не задерживают независимые операции остальных. Оператор видит состояние и может приостановить нужную связку; неопределённая отправка остаётся на ручном разборе.
- После перезапуска сервера очередь сохраняется, уже отправленное не дублируется, новые сообщения доставляются; ошибки `failed`/`uncertain` видны ответственному.
- Webhook-подписки, сертификат и резервное восстановление проверены. Доступ к серверу и токенам ограничен; согласованы срок хранения и правила работы с персональными данными.
