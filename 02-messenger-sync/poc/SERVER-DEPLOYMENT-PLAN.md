# План доработки и размещения моста Telegram ↔ MAX

Согласованное описание сервиса приведено в [README](../../README.md). Здесь зафиксированы выполненные D1–D4, текущая постановка D5, оставшиеся доработки и порядок размещения на одном сервере заказчика.

Статус на 30.10.2026: **D1–D4 выполнены, прошли независимую приёмку и слиты в `main`; D5.1 и D5.2 реализованы в отдельных ветках, завершающие проверки закреплены в штатном наборе; независимая приёмка полного D5 ещё впереди**. Развёртывание на сервере заказчика ещё не выполнено. Разработчик заказчика получил доступ к репозиторию и предложил существующий сервер; его ОС, архитектура, ресурсы, сеть, HTTPS-адрес и доступ ещё не подтверждены. Требования к площадке приведены в [OPERATIONS](OPERATIONS.md#требования-к-серверу).

Главная цель пользователя: **мост работает круглосуточно, даже когда ноутбук выключен**. Сначала переносим текущую тестовую версию на сервер заказчика через Docker и Makefile; затем реализуем webhook для рабочего режима. Приложение работает рядом с сайтом на сервере, а не как файл в каталоге веб-страниц. Ноутбук перестаёт быть необходимым только после проверки серверного экземпляра и остановки локального.

Текущий [локальный прототип](HOW-IT-WORKS.md) получает события опросом API и использует SQLite для очереди. Для рабочего размещения нужно изменить способ получения событий: по [документации MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions) Long Polling не подходит для production; предусмотрен Webhook. Telegram также [поддерживает webhook](https://core.telegram.org/bots/api#setwebhook).

Актуализация 20.10.2026: карантин, операторские команды, `health`, локальный монитор stdout/JSONL и независимые сетевые задачи реализованы. Async-версия прошла живой тест на двух группах с 44 доставками; расширенная приёмка остаётся частичной. Локальные фоновые процессы пока не являются системными службами.

Текущий runtime использует `asyncio` и зафиксированный `aiohttp`. Webhook пока не реализован: запланирован один `aiohttp`-сервер с двумя маршрутами. Внедрение aiogram/maxapi отложено. При переходе `health` должен проверять доступность приёма и подписки; отсутствие новых сообщений само по себе не считается отказом webhook.

### Результат и границы изменений

Команда заказчика может собирать, запускать и проверять текущий мост через Docker Compose и Makefile, без установки окружения Python на сервере. D1 включает Dockerfile, compose.yaml, Makefile, `.dockerignore`, поддержку конфигурации контейнера, проверки и инструкции. Работоспособность на конкретном сервере заказчика проверяется при размещении.

Изменения runtime ограничены чтением конфигурации и запуском в контейнере. Сохранены одна пара групп, текущие тексты/фото/reply, схема базы, порядок очереди и правила `uncertain`. Автоматический повтор неопределённых публикаций, очистка данных, поддержка каналов и смена стека остаются за пределами D1.

### Реализованный объём

1. **Образ.** Зависимости установлены по `uv.lock`. Приложение работает без root (UID/GID `10001:10001`), с файловой системой только для чтения. `.dockerignore` исключает секреты, локальное состояние, базы, резервные копии, логи и `.venv`; HTTPS-сертификаты учтены, рабочие токены в образ не включены.
2. **Конфигурация.** Параметры читаются из окружения контейнера; закрытый `.env` служит источником для Compose. Окружение имеет приоритет, пустые обязательные значения отклоняются без вывода секретов. `BRIDGE_STATE_DIR` задаёт каталог состояния, для сертификата MAX документировано монтирование файла. Файловые Docker secrets в D1 не добавлялись.
3. **Compose.** `bridge` и `monitor` используют общий постоянный volume `/state`. Настроены права записи, перезапуск после выхода процесса и передача SIGTERM через `init`; Compose ждёт завершения до 60 секунд при 30-секундном окне приложения. Публичных портов, privileged-режима и Docker socket у контейнеров нет.
4. **Makefile.** Реализованы `build`, `up`, `down`, `update`, `logs`, `status`, `health`, `test`, `smoke`, `stand`, `doctor`, `discover`, `stop-bridge` и `cli`. Команды используют выбранный `PROJECT`; остановка и обновление сохраняют volume, неудачная сборка оставляет работающую версию. Защита стенда отказывается от очистки при конфликте имени, чужих ресурсах или ошибке их перечисления Docker.
5. **Healthcheck.** Docker healthcheck, monitor и команды `make health`/`make status` используют общие пороги. Исправная пустая очередь допустима; блокирующая ошибка, старая очередь и устаревший heartbeat видны как проблема. Проверка не публикует сообщения. Внешние оповещения и автоматический перезапуск при `unhealthy` в D1 не добавлялись.
6. **Проверки и документация.** Прошли 92 теста, прежние smoke-стенды, регрессии защиты/CLI и отдельный контейнерный прогон. README и эксплуатационные документы описывают конфигурацию, команды Make, постоянный volume и ограничения тестового polling.

## Порядок передачи и проверки задач

Каждая следующая задача передаётся Devin отдельно, с согласованным объёмом и отдельной веткой от актуальной `origin/main`. Результат — draft PR в `main` без автоматического слияния и без развёртывания на сервере заказчика. Devin самостоятельно не сливает PR; включение изменений в `main` выполняется после независимой проверки отдельным действием владельца репозитория. PR содержит описание, соответствие критериям задачи, точные команды и результаты, ограничения и список незавершённых проверок. Рабочие боты, существующая `.state` и токены разработчика или заказчика для реализации не используются: стенды и тестовые данные изолированы.

После получения PR проверяющий фиксирует SHA его вершины, изучает diff и тесты, затем независимо выполняет проверки этой версии в доступном Docker-окружении. Замечания возвращаются Devin как воспроизводимые сценарии с ожидаемым и фактическим результатом. После исправления проверяются затронутые сценарии и регрессия. Реальный обмен на выбранной паре тестовых групп и серверная приёмка идут отдельным согласованным прогоном; их нельзя подменять стендом или автоматически включать при просмотре PR.

Для передачи нужны доступ Devin к репозиторию и наличие этих документов в доступном ему коммите либо их передача вместе с заданием; это проверяется перед стартом. Прямой интеграции с Devin в текущей сессии нет: пользователь запускает задачу, а результат передаётся ссылкой на PR. Никакие действия в Devin этим документом не запускаются.

### Цель и границы D2

При временном отказе Telegram или MAX безопасные операции повторяются с управляемой задержкой и продолжаются после восстановления. Принятые сообщения остаются в SQLite, исправные независимые операции другой платформы и heartbeat продолжают работать. Если запрос мог опубликовать сообщение, результат сохраняется как `uncertain` без автоматического повтора — действующая политика FR-07 сохраняется.

«Сообщения не теряются» в D2 означает сохранение принятых задач и курсоров, отсутствие удаления/пропуска при ошибке и корректное возобновление безопасной обработки. Автоматическая доставка после неопределённой публикации не обещается. Получение ещё не прочитанных событий зависит также от срока их хранения платформой; нельзя подтверждать или сдвигать курсор несохранённого события.

Объём: текущая одна пара групп, polling, текст/фото/reply, существующие Python/asyncio/aiohttp и SQLite. Расширение на каналы и несколько связок, webhook, backup/restore, очистка базы, новые внешние сервисы и полная переработка логирования относятся к другим задачам. Использовать существующий транспорт, очередь и стенды; общую библиотеку автоматического повторения запросов поверх публикации не добавлять.

### Исходные механизмы и обнаруженные пробелы D2

Перед D2 в коде уже были отдельные poller/sender для обеих платформ, ограниченные HTTP-таймауты, backoff опроса, обработка Telegram `parameters.retry_after`, `429` и `attachment.not.ready`, сохранение ожидающей задачи, пауза при 401/403 в опросе и `uncertain` после неоднозначной публикации. В D2 эти механизмы расширены и проверены.

До D2 `Api.read` возвращал статус и тело, но терял HTTP `Retry-After`; сетевые ошибки до соединения и после возможной публикации объединялись в `TransportError`; для ошибок подготовки фото использовалась фиксированная задержка, а счётчик публикаций не отражал все попытки подготовки. Подготовка фото выполнялась заново при каждом `deliver`. Эти пробелы закрыты; восстановление после `attachment.not.ready` без постоянной повторной загрузки проверено при приёмке.

### Требуемое поведение

| Ситуация | Поведение |
|---|---|
| Временный сбой опроса, скачивания или подготовки фото | Управляемый повтор с backoff; курсор несохранённого события не продвигается, задача остаётся ожидающей. |
| Доказано, что соединение для публикации не установлено и запрос не отправлен | Задача остаётся `pending`, повторяется после задержки. Доказательство основано на конкретной фазе/типе ошибки и проверяется тестом. |
| API определённо отклонил запрос: 429 или `attachment.not.ready` | `pending`; соблюдается срок следующей попытки. Для неготового вложения повтор использует уже подготовленное вложение, пока оно пригодно, без постоянной загрузки нового файла. |
| Публикация могла состояться: потерян/просрочен ответ, 5xx после отправки, некорректный успешный ответ или нет ID копии | `uncertain`, автоматических повторов публикации нет. Один лишь 5xx или общий `TimeoutError` не доказывает, что сообщение не создано. |
| Постоянная ошибка авторизации, прав, запроса, медиа или проверки сертификата | Сохранённая задача/ошибка, понятная безопасная диагностика и управляемая остановка соответствующей операции либо пауза платформы. Бесконечный частый повтор не допускается; проверка TLS не отключается. |
| Ошибка SQLite или программы | Не маскируется сетевым retry; сохраняется существующее безопасное завершение runtime без ложного подтверждения обработки. |

Безопасность повтора определяется операцией и фазой, а не только HTTP-методом: например, текущий Telegram `getUpdates` использует POST, но не публикует сообщения. Редиректы, middleware или HTTP-библиотека не должны скрыто повторять запрос публикации. Прерывание при незавершённом `sending` сохраняет консервативное восстановление в `uncertain`.

Требования к задержкам и ошибкам:

- Разделять платформу, операцию, HTTP-статус, безопасный машинный код API и наличие неопределённости. Не переносить в исключения/логи сырые тела ответов, токены, тексты сообщений или приватные URL.
- Учитывать Telegram `parameters.retry_after` и стандартный HTTP `Retry-After`, если он присутствует: секунды либо HTTP-date. Формат MAX не выдумывать по аналогии с Telegram. Если есть несколько корректных указаний, не повторять раньше максимального срока; собственный предел backoff не сокращает обязательное ожидание сервера. Пустые, отрицательные, bool, NaN/Infinity, неверные даты и непредставимые значения должны обрабатываться без падения и без цикла немедленных повторов.
- Для временных безопасных сбоев использовать положительный ограниченный экспоненциальный backoff с ограниченным случайным разбросом. Счётчик последовательных сбоев должен работать и до публикации, включая подготовку фото; после успеха соответствующей операции он сбрасывается. Область ожидания документировать, здоровая другая платформа не ждёт вместе с ошибочной.
- Ожидание не блокирует event loop и прерывается штатной остановкой. Время следующей попытки ожидающей задачи сохраняется в SQLite; пересоздание контейнера не обнуляет уже назначенный срок повтора. Сохранить порядок доставки и существующие ограничения частоты успешных отправок.
- Использовать существующие `ready`, состояния и механизмы Store; любые необходимые изменения состояния должны быть минимальными и совместимыми с существующей базой. Новые эксплуатационные параметры, если они нужны, читать из конфигурации, валидировать и описать в `.env.example` и README. В тестах часы и случайность должны управляться без длительных реальных ожиданий.

### Первичные источники для D2

Сверены при постановке 28.10.2026; Devin перепроверяет их перед изменением обработки ошибок:

- [RFC 9110, Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3): поддерживаемые формы заголовка — delay-seconds и HTTP-date.
- [aiohttp: исключения клиента](https://docs.aiohttp.org/en/stable/client_reference.html#client-exceptions): различия ошибок соединения, сертификата и таймаутов. Безопасность повтора конкретной операции дополнительно подтверждается анализом используемой версии и тестами.

### Цель и границы D3

Принятое событие и все данные для его дальнейшей доставки сохраняются до продвижения курсора. После перезапуска продолжается безопасная обработка, подтверждённые отправки не повторяются, собственные копии ботов не возвращаются по кругу. Гарантия относится к успешному COMMIT на исправном постоянном локальном volume одного хоста; неисправность/утрата самого диска и срок хранения ещё не полученных событий платформой остаются внешними ограничениями.

Объём — текущая одна пара групп, polling, текст/фото/reply, существующие Python/asyncio/aiohttp и SQLite. Сохранить результаты D1/D2, порядок очереди, сроки безопасных повторов и политику `uncertain`. После аварии незавершённый `sending` остаётся неопределённым даже при остановке до фактического POST: отсутствие публикации нельзя выводить только из перезапуска. Автоматическая доставка ровно один раз при потерянном результате API не обещается.

Каналы, несколько связок, webhook, новые брокеры/БД, автоматическое разрешение `uncertain`, retention/очистка, backup/restore и полная переработка логирования относятся к другим задачам. Не добавлять архив всех исходных сообщений или второй слой очереди без доказанной необходимости: существующих `jobs` и `quarantine` достаточно, если они сохраняют всю информацию для согласованной дальнейшей обработки.

### Существующая основа и предмет аудита

`Store.accept` сохраняет задачи, карантин и курсор одной транзакцией; `inbox` и уникальность частей задач защищают от повторного приёма. `start_sending` атомарно захватывает только готовую голову очереди перед публикацией. `update` сохраняет результат и ID копии; `recover` переводит `sending` в `uncertain`. Есть WAL, привязка базы к ботам/чатам, файловая блокировка процесса, read-only просмотр и миграция старой схемы с копией перед изменением.

Тесты уже проверяют rollback пакета, карантин, ошибку записи результата, ограниченное ожидание блокировки SQLite, дедупликацию, старую схему и запрет изменения при работающем мосте. ### Требуемые инварианты

- **Приём:** курсор/marker, признак дедупликации и полный набор частей принятого сообщения либо его карантин сохраняются согласованно. Ошибка записи/COMMIT не оставляет продвинутый курсор с потерянными задачами или частично сохранённое сообщение. Неожиданная ошибка программы не превращается молча в карантин.
- **SQLite:** явно установить и проверить WAL и `synchronous=FULL` для записывающих соединений, не полагаться на неявные defaults конкретной сборки SQLite. Это не отменяет зависимость от исправности файловой системы и реализации fsync. Ошибка применения настроек/открытия/миграции останавливает запуск с безопасной диагностикой; база не удаляется и не пересоздаётся поверх существующей. Ограниченное ожидание блокировки сохраняется; ошибка хранилища не становится бесконечным сетевым retry.
- **Публикация:** перед внешним побочным эффектом сохранён `sending`; `sent` появляется только вместе с проверенным ID копии. Ошибка записи после принятия запроса платформой не вызывает повторный POST; после аварии остаётся `uncertain`. Предыдущие подтверждённые части и их соответствия ID сохраняются.
- **Восстановление:** `pending` и его `ready`, `sent`, `failed`, `uncertain`, `skipped`, курсоры, связи ответов, карантин и аудит переживают перезапуск. `recover` идемпотентен и не возвращает подтверждённые/неопределённые задачи в автоматическую отправку. Во время подготовки фото допустима повторная подготовка; публикация копии проверяется отдельно.
- **Дедупликация и цикл:** одно входное ID создаёт один набор задач, включая повтор пакета и перезапуск. Два одинаковых человеческих текста с разными ID остаются двумя сообщениями. Эхо именно собственных ботов игнорируется в обе стороны; сообщения людей и других ботов не отбрасываются общим фильтром всех ботов. Reply продолжает ссылаться на сохранённую копию, включая подтверждение `uncertain` штатной командой.
- **Один владелец:** второй контейнер с тем же volume не начинает опрос и публикацию. После SIGKILL блокировка освобождается ОС, ручное удаление lock-файла не требуется. Чтение status/health/monitor/queue list не мигрирует базу и не меняет состояния доставки. Несовместимая привязка ботов/чатов отклоняется до обработки очереди.
- **Совместимость:** использовать текущую схему 3, если исправления не требуют её изменения. При необходимости — явная версия, атомарная миграция и сохранение всех данных/сроков/ID; существующая копия перед миграцией сохраняется. Не сбрасывать volume, курсоры или очередь ради обновления. Разработка операторского backup/restore остаётся D9.

### Первичные источники для D3

Сверены при постановке 28.10.2026; перед реализацией проверить применимость к SQLite внутри зафиксированного образа:

- [SQLite WAL](https://www.sqlite.org/wal.html): журнал и совместное использование файлов базы на одном хосте.
- [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous): различия FULL/NORMAL и гарантии завершённого COMMIT в WAL; они зависят от корректности хранилища.
- [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html): границы транзакции и предположения о файловой системе; не подменять аварийный тест обычным закрытием соединения.

### Контракт health и диагностики D4

- **Общее состояние.** Сохранять существующие коды и поля, где возможно; новые поля добавлять совместимо. Показать состояние процесса, heartbeat, каждого получателя/отправителя и обеих платформ; очередь, её возраст, голову и блокировку. `status` сообщает диагностический результат; `health` возвращает ненулевой код при проблеме. Недоступная/отсутствующая/несовместимая база — диагностируемое нездоровое состояние, без падения с приватным traceback и без создания новой базы.
- **Прогресс worker.** Учитывать фактический прогресс самого worker, текущую фазу, начало операции и допустимый срок завершения/пробуждения. Обновление общего heartbeat не доказывает работоспособность poller/sender. Детерминированно обнаруживать зависание одного из них в пределах документированного порога с учётом таймаутов операции; остальные worker и heartbeat в этом тесте продолжаются. Не имитировать прогресс worker из heartbeat. Общая остановка event loop по-прежнему обнаруживается устаревшим heartbeat.
- **Ожидание и простой.** Успешные пустые опросы и отсутствие исходящих сообщений не являются отказом. Для ожидающего `pending` показать `retry_at`/оставшееся ожидание и безопасную причину, отдельно от зависания. Соблюдать полный серверный `Retry-After`, включая срок больше суток; не сокращать его ради healthcheck. Длительная очередь или ошибка платформы могут оставлять health нездоровым, но запланированное ожидание не объявляется зависшей операцией.
- **Причина и действие.** Для проблем показать платформу/направление, фазу (`poll`, подготовка фото, публикация, хранилище), безопасный код/класс, затронутый `job_id`, срок безопасного повтора либо признак паузы/ручной сверки. Отличать 429, временный отказ соединения, таймаут после начала публикации, 401/403, TLS, зависание worker, блокировку очереди и ошибку SQLite. По этим полям оператор должен найти нужную задачу штатной командой и выбрать действие по OPERATIONS без чтения исходников.
- **Пороги и восстановление.** Docker healthcheck, `make health`, `make status` и monitor используют одинаковые эффективные пороги. Существующие значения не менять без обоснования; дополнительные параметры, если нужны, документировать и передавать единообразно. После нового запуска старые telemetry/паузы не выдавать за состояние новых worker; при этом не терять задачи, `ready`, курсоры, связи, аудит и нерешённые ошибки доставки.
- **Чтение.** Диагностические команды не выполняют API-запросы, миграцию, `recover`, публикацию или изменение данных/схемы/состояний доставки. Чтение WAL/SHM допустимо по принятому D3 критерию логического снимка. Сохраняемые worker-метаданные ограничены фиксированным числом записей и не требуют новой таблицы для каждого запроса.

### События monitor и действия оператора

Развивать текущий monitor/outbox, сохраняя problem/recovery и `event_id`. Одна неизменная причина не создаёт новое оповещение на каждом цикле из-за роста возраста, смены номера попытки или обратного отсчёта. Изменение существенной причины фиксируется, восстановление фиксируется после подтверждающего наблюдения. Перезапуск monitor не создаёт повтор той же проблемы; сбой sink сохраняет недоставленную запись для последующей выдачи. Не обещать exactly-once при сбое после записи в sink: возможный повтор имеет тот же `event_id`.

Недоступность базы не является подтверждением устранения уже известных проблем. Сохранить совместимость `alerts.jsonl` и описать, какие события попадают в stdout/stderr и файл. Внешний канал доставки и конкретный получатель не подключаются в D4.

В OPERATIONS дополнить краткую таблицу «код/симптом → команда проверки → действие»: исправный тихий чат; временный сбой и ожидание повтора; 429 с большим сроком; пауза из-за прав/TLS; зависший получатель/отправитель; `failed`/`uncertain`; недоступное хранилище. Не предлагать слепой повтор неопределённой отправки, удаление базы/volume или автоматический перезапуск как универсальное лечение.

### Требуемое поведение D5

- **Один владелец записи.** Автоматическое обслуживание каждой базы выполняет существующий владелец её записи, небольшими транзакциями с ограниченным объёмом работы за цикл. Не вводить cron, отдельный контейнер/сервис, второй writer/checkpointer или бесконтрольный фоновый поток. Мост, heartbeat и независимая доставка продолжают работать во время обычной очистки; длинная транзакция не маскируется обновлением telemetry.
- **Сохранность.** Очистка идемпотентна; авария откатывает незавершённую транзакцию. Сохранить WAL, `synchronous=FULL`, атомарность пакета/курсора, привязку чатов, блокировки, статусы и `ready`, правила backoff/Retry-After/uncertain. После удаления содержимого штатные read-only команды показывают явный признак очистки и метаданные, без KeyError/некорректного JSON. ID задач не переиспользуются; ссылка аудита/ответа не начинает указывать на другую запись.
- **Реальный объём.** Учитывать обе SQLite, их WAL/SHM, управляемые файлы alerts и временные файлы; показывать свободные байты именно файловой системы volume. Удаление строк освобождает страницы для повторного использования, но само по себе не обещает уменьшения файла. Выбрать минимальный безопасный способ переиспользования/освобождения страниц и checkpoint; не выполнять тяжёлый полный VACUUM при активной доставке или нехватке места. Длительный reader/BUSY и невозможный checkpoint диагностировать, не удалять WAL/SHM вручную.
- **Контроль роста.** Добавить настраиваемые предупреждающий/критический пороги размера управляемых данных и резерв свободного места. Для порогов предложить конкретные консервативные значения и обосновать их в карте анализа до реализации; владелец уточнил 29.10.2026: до 2 ГБ выделяется только для данных `/state`, Docker-образы/кэш/логи хранятся отдельно, резервные копии размещать отдельно. Начальные пороги D5.1 сохраняются: объём 256/512 МиБ, свободное место 256/128 МиБ; достаточность бюджета проверить по росту данных после очистки. При квоте проверить соответствие метрик доступному по ней месту. На критическом пороге не вычитывать новые пакеты, которые нельзя устойчиво сохранить; уже принятые задачи не удалять. Описать ограниченное ожидание/возобновление после освобождения места без busy loop и без ложного успеха. При реальной ошибке записи транзакция и курсор откатываются по D3. Бесконечный приём без роста хранилища не обещается: минимальные ID и нерешённая очередь продолжают занимать место, а срок хранения ещё не принятых событий ограничен API.
- **Диагностика.** Health/status и существующий monitor показывают объёмы, пороги, свободное место, последний результат обслуживания и безопасный код проблемы. Ошибка самой проверки диска не считается исправностью. Изменение количества байтов не порождает новое problem каждый цикл; recovery подтверждается по правилам D4. Просмотр и dry-run не меняют логический снимок БД, не выполняют checkpoint/миграцию/recover и не обращаются к API. Новые поля/коды встраивать в контракт D4, без содержимого задач/секретов.
- **Файлы.** Для alerts.jsonl — ограниченная ротация по размеру, возрасту и числу архивов, очистка истории старше 90 дней даже в тихом сервисе; ограничение размера может сократить доступную историю, что указать в документации. Не терять ещё не выданный outbox при ротации/аварии. `/tmp` контейнеров ограничить явно; существующий лимит фото 10 МиБ сохранить. Если медиа сейчас обрабатываются в памяти, не добавлять дисковый кеш ради его очистки. Удалять только собственные временные файлы с безопасно определённым владельцем/путём, без перехода по symlink за пределы каталога.
- **Штатная остановка.** После SIGTERM новые API-операции и новые пакеты обслуживания не начинаются. Активная короткая транзакция завершается либо откатывается; общий 30-секундный бюджет приложения и запас Compose 60 с сохраняются. Прерванная подготовка фото остаётся pending, возможная публикация — uncertain, без автоповтора. Штатно закрыть соединения БД/HTTP и оставить состояние для следующего запуска; финальный JSON-лог не раскрывает секреты. Нехватка места при завершающей записи не выдаётся за успешное сохранение.
- **Ручная проверка через Make.** Добавить штатный dry-run обслуживания и явное применение через Makefile. Dry-run по умолчанию только показывает количества/причины без содержимого; фактическое обслуживание требует отдельного флага и владения блокировками нужных БД, при работающих владельцах отказывает. После применения обычный запуск восстанавливает обработку. Обычные `down`/`update` сохраняют volume; команды D5 не удаляют volume, бэкапы и чужие Docker-ресурсы.

Объём — текущая одна пара групп с polling, Python/asyncio/aiohttp/SQLite, Docker + Makefile. Не входят каналы, несколько связок, webhook, Go, новая политика повторов, автоматический повтор uncertain, подключение внешних оповещений и серверный релиз. Полные backup/restore и перенос `.state` остаются D9; согласованная копия и проверка перехода обязательны в D5, если нужна миграция. Переиспользовать существующие механизмы и стенды, не добавлять библиотеку/службу без доказанной необходимости.

### Первичные источники для D5

Сверены при постановке 29.10.2026; перед реализацией сопоставить с реальными версиями в образе:

- [SQLite PRAGMA](https://sqlite.org/pragma.html): auto_vacuum/incremental_vacuum, freelist/page_count, journal_size_limit и режимы checkpoint; не считать уменьшение числа строк уменьшением размера файла.
- [SQLite WAL](https://sqlite.org/wal.html): checkpoint, рост WAL при долгих readers, запрет ручного удаления WAL и известные ограничения версии. В принятом образе SQLite 3.40.1: отдельно проверить применимость описанного WAL-reset bug при предложенной схеме обслуживания; не добавлять конкурентный writer/checkpointer к той же базе. Если устранение риска требует обновления runtime, обосновать точную минимальную правку и повторить регрессии D1–D4.
- [SQLite VACUUM](https://sqlite.org/lang_vacuum.html): требования к месту/блокировкам и ограничения операции; полное уплотнение не выполнять скрыто при каждом старте.
- [Docker tmpfs](https://docs.docker.com/engine/storage/tmpfs/): размер/права временного mount; tmpfs расходует память и не заменяет постоянный volume.

Остановить локальный экземпляр перед переключением тех же ботов; проверить работу при выключенном ноутбуке и после перезагрузки сервера.

После каждого изменения кода: подходящие автоматические тесты → отдельный сквозной прогон нового кода → обновление существующей документации. Живые проверки выполняются в явно выбранных тестовых чатах и каналах; рабочие связки подключаются после приёмки. Код и документы разделяют реализованное поведение и запланированные возможности.

Предварительный ориентир — около десяти рабочих дней одного разработчика при готовых доступах и перечисленном объёме; ожидание доступов, согласования и дополнительные типы содержимого в оценку не входят.

## Порядок размещения

1. Передать администратору [требования к серверу](OPERATIONS.md#требования-к-серверу) и проверить соответствие площадки **этапу 1** из OPERATIONS. При отсутствии подходящего места рассмотреть отдельную VM или VPS.
2. Подготовить учётную запись для развёртывания, код из приватного репозитория и постоянный volume состояния. Сборку и эксплуатацию выполнять через Makefile по README; Python-зависимости уже находятся в Docker-образе. Согласовать защищённую передачу `.env` и при необходимости монтирование сертификата MAX; токены не передавать через Git.
3. Сверить очередь и ошибки `uncertain`, остановить локальный мост и монитор, сделать согласованную копию SQLite, перенести базу из `.state` в volume `/state` и передать секреты. Процедура миграции в volume ещё требует подготовки и проверки. Выполнить `make doctor` до запуска, затем `make up` для **одного** polling-моста и монитора. Через `make health` и `make status` проверить состояние, восстановление после перезапуска и доставку в обе стороны при выключенном ноутбуке. Если связь ответов со старыми сообщениями не нужна, можно начинать с новой базы только после осознанного решения владельца.
4. После тестового переноса проверить соответствие **этапу 2**: постоянный публичный HTTPS-адрес, сертификат и маршруты. Реализовать webhook, проверку секретов и устойчивую запись до подтверждения; подключить внешний канал оповещений, резервное копирование и правила хранения.
5. Проверить webhook сначала на тестовой паре групп и тестовой паре каналов, затем на всех согласованных связках. Проверить оставшиеся сценарии живой приёмки, переключение и откат. К ограниченному рабочему пилоту переходить только после выполнения критериев готовности ниже.

## Домен и работа без ноутбука

Для SSH и исходящих запросов текущего polling-моста достаточно доступа сервера в сеть: тестовый мост можно перенести без домена и входящего порта. Такой промежуточный запуск сохраняет ограничения polling MAX и не является рабочим размещением. Используется тот же код и очередь; перенос пока не выполнялся.

Для целевого webhook нужен постоянный публичный HTTPS-адрес с доверенным сертификатом, доступный MAX и Telegram. Отдельный поддомен и покупка нового домена необязательны: можно выделить два пути на существующем домене заказчика, например `https://example.ru/bridge/telegram` и `https://example.ru/bridge/max`, и направить их через reverse proxy к приложению. Поддомен — другой допустимый вариант. Также можно использовать постоянное имя от хостинга с подходящим сертификатом; наличие такого имени у рассматривавшегося тарифа REG.RU **не подтверждено**. Если подходящего адреса нет, потребуется обеспечить его отдельно.

Работа MAX webhook напрямую по IP с сертификатом на IP **не подтверждена**. В документации MAX указано совпадение доменного имени URL с CN/SAN сертификата; поэтому URL с голым IP не считаем готовым решением для рабочего запуска. Собственный сайт и интерфейс для участников не нужны: адрес используется только для доставки событий в мост.

## Предлагаемая схема первого серверного варианта

```text
Telegram ──HTTPS webhook──┐
                          ├── домен:443 → HTTPS-сервер → проверка секрета → SQLite-очередь
MAX ───────HTTPS webhook──┘                                          │
                                                                    ▼
                                                      планировщик отправок по чатам
                                                          ↙          ↘
                                                    Telegram API    MAX API
```

Один Linux-сервер или VM, одно постоянное имя с HTTPS, один экземпляр моста с независимыми очередями целевых чатов и ограниченной параллельной отправкой. Обработчик webhook проверяет секрет и допустимость запроса, сохраняет событие в SQLite и только **после записи** возвращает успешный ответ. Отправка на другую площадку выполняется отдельно из устойчивой очереди с общими ограничениями каждой платформы. Существующие правила сопоставления ответов, пометки автора, исключения собственных сообщений и защиты от дублей расширяются на несколько связок. SQLite сохраняется до появления подтверждённой потребности в другом хранилище.

Для MAX endpoint должен быть доступен по **HTTPS на порту 443**, с сертификатом доверенного УЦ, совпадающим доменным именем и полной цепочкой. MAX требует ответ `200 OK` не позднее 30 секунд; для подписки можно задать `secret`, который приходит в `X-Max-Bot-Api-Secret`. При неудаче MAX повторяет доставку, но после восьми часов без успешного ответа может снять подписку — её состояние нужно проверять и оповещать ответственного. [Официальные требования MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions). Для Telegram `setWebhook` поддерживает `secret_token` с заголовком `X-Telegram-Bot-Api-Secret-Token`; при webhook `getUpdates` одновременно не работает. [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).

## Что требуется подготовить для webhook и рабочего режима

1. Linux-сервер или VM с постоянным локальным диском, публичным HTTPS-входом на порту 443 и исходящими HTTPS-запросами к Telegram и MAX. Для webhook — постоянное DNS-имя с доверенным сертификатом и маршрутизацией к приложению. Существующий reverse proxy может принимать HTTPS:443 и передавать запросы внутреннему приложению; отдельный публичный IP для VM тогда не требуется. По уточнению владельца от 29.10.2026 до 2 ГБ выделяется только под данные моста (`/state`); Docker-образы, кэш и Docker-логи хранятся отдельно, резервные копии размещать отдельно. Проверить рост данных и доступное по квоте место, согласовать лимиты CPU/RAM с учётом работы Битрикс на том же сервере.
2. Доступ администратора по SSH-ключу для настройки ОС. Открыть 443; SSH ограничить ключами и, если возможно, доверенными адресами. Настроить автоматическое обновление TLS-сертификата и проверку продления. Токены ботов и секреты webhook передавать только через защищённый канал/хранилище, **не в чат и не в Git**.
3. Разработать и протестировать два HTTP-обработчика webhook; изменить текущий цикл polling на приём событий. Для каждого события — валидация, запись до `200`, дедупликация по ID и отдельная отправка из очереди. Сохранить текущую обработку неоднозначного результата отправки `uncertain` для ручного разбора.
4. Использовать принятую в D1 Docker-поставку через Makefile, настроить автозапуск Docker после перезагрузки и проверить перезапуск контейнеров после сбоя. Использовать `make health` и события монитора для очереди/процесса; подключить внешний канал и получателя оповещений. Дополнить проверками действительности обеих webhook-подписок, срока сертификата и места на диске. Логи не должны содержать токены, тексты переписки и приватные URL вложений.
5. Делать резервные копии SQLite согласованным способом, шифровать и проверять восстановление. До переноса реальной переписки определить срок хранения текстов, ID, имён и медиа-ссылок, круг доступа, место размещения и порядок удаления данных. Текущий прототип автоматически данные не очищает.

## Переключение и откат

Перед **первым переносом на сервер** остановить локальный процесс: **два экземпляра с одними ботами запускать нельзя**. Убедиться, что очередь опустела и нет `uncertain`; сделать согласованную резервную копию SQLite и перенести базу вместе с настройками. При запуске с пустой базой ответы на старые сообщения могут превратиться в текстовую цитату. Перенос `bridge.sqlite3` после остановки исключает расхождение с продолжающим запись локальным процессом; `MAX_CA_FILE` на сервере должен указывать на существующий доверенный сертификат, если он нужен.

Для **перехода с серверного polling на webhook** поднять HTTPS endpoint и службу, зарегистрировать webhook Telegram и подписку MAX на тестовые группы. При смене режима не использовать `drop_pending_updates`: это намеренно удаляет ожидающие события Telegram. Проверить доставку, ответы, фото, повторную доставку одного webhook, отсутствие циклов и восстановление после перезагрузки. Откат — остановить активный экземпляр и вернуть один согласованный способ получения событий, проверив очередь, базу и подписки.

## Критерии готовности

- При остановленном локальном мосте и выключенном ноутбуке новые сообщения продолжают проходить через сервер; база и монитор находятся на сервере заказчика или выбранной VM. Обновление и наблюдение за сервисом не требуют постоянного SSH-сеанса.
- На всех согласованных связках новые тексты и фото с подписями проходят **в обе стороны**; ответы в группах связаны с правильными сообщениями, канальные публикации можно создавать на любой площадке. Каждый принятый исходный пост создаёт одну доставку в парную площадку, без возврата по кругу и попадания в другие связки; длинный пост может разбиваться на несколько частей по текущим правилам. Комментарии под канальными постами в эту приёмку не входят.
- Активный чат или `failed`/`uncertain` одной связки не задерживают независимые операции остальных. Оператор видит состояние и может приостановить нужную связку; неопределённая отправка остаётся на ручном разборе.
- После перезапуска сервера очередь сохраняется, уже отправленное не дублируется, новые сообщения доставляются; ошибки `failed`/`uncertain` видны ответственному.
- Webhook-подписки, сертификат и резервное восстановление проверены. Доступ к серверу и токенам ограничен; согласованы срок хранения и правила работы с персональными данными.

D1 принят и слит в `main` 28.10.2026; до переноса нужно подтвердить требования к серверу заказчика и выполнить серверную и живую проверки новой поставки. Подготовка инфраструктуры может идти параллельно оставшимся доработкам. Рабочее переключение выполняется после разработки и проверки серверного приёма. Требования HTTPS и webhook сверены 21.10.2026; перед переключением проверить их повторно и подтвердить фактическую доступность endpoint.
