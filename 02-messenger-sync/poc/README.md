## Подготовка

Токены отдельных тестовых ботов находятся в `02-messenger-sync/.env` (исключён из Git, права 0600). Оба проверены через API: Telegram `max_tg_2sync_bot` (8855739635), MAX `se14620006_1_bot` (531649697). Дополнительный сертификат настроен только для MAX, проверка HTTPS проходит. Webhook-подписок нет. Обе группы и права проверены. Живой обмен текстом и фотографиями подтверждён 19.10.2026; см. [протокол](LIVE-TEST-2026-10-19.md). Ранее присланная ссылка MAX `se14620006_biz` ведёт на канал и не используется как username бота.

Добавить ботов в закрытые тестовые группы. Telegram: отключённый Privacy Mode или роль администратора, разрешены текст и фотографии. MAX: администратор с `read_all_messages`, отправка проверяется в тестовом чате. Право `write` в группах разрешает редактирование/удаление и для обычной отправки не требуется: [ChatMember](https://dev.max.ru/docs-api/objects/ChatMember). В существующих webhook-подписках программа ничего не меняет; при их наличии останавливается для проверки.

Команды из корня репозитория:

```sh
rtk proxy python3 02-messenger-sync/poc/bridge.py doctor
rtk proxy python3 02-messenger-sync/poc/bridge.py discover --seconds 90
```

`doctor` проверяет токены и подписки без отправки сообщений. `discover` выдаёт одноразовую фразу. Отправьте её обычным участником в каждую тестовую группу, пока команда выполняется. Программа сохранит ID только групп с этой фразой, не публикуя ответы и не сохраняя содержимое чужих сообщений. Поиск читает/подтверждает тестовую очередь событий ботов, поэтому не использовать с рабочими ботами.

```sh
rtk proxy python3 02-messenger-sync/poc/bridge.py bind
rtk proxy python3 02-messenger-sync/poc/bridge.py doctor
rtk proxy python3 02-messenger-sync/poc/bridge.py run
```

`bind` записывает найденную пару групп в локальный `.env`. `run` проверяет права и начинает перенос. Остановка — Ctrl+C; очередь остаётся в `.state/bridge.sqlite3`. Повторный запуск использует сохранённые указатели событий. Блокировка файла исключает параллельные процессы этого прототипа.

```sh
rtk proxy python3 02-messenger-sync/poc/bridge.py status
rtk proxy python3 02-messenger-sync/poc/bridge.py health --json
rtk proxy python3 -m unittest discover -s 02-messenger-sync/poc -p 'test_*.py' -v
rtk proxy python3 02-messenger-sync/poc/smoke_p0.py
```

## Что переносится

- Новые обычные тексты и фотографии всех участников. Подпись автора и площадки включается в копию. Ограничение картинки в PoC — 10 MiB; MIME JPEG, PNG или WEBP. Фактическое принятие размера/формата дополнительно проверяется платформами; автоматического преобразования нет.
- Подписи к картинкам; длинный текст разбивается с учётом ограничений Telegram для Unicode. Изображения одного альбома могут стать отдельными сообщениями; исходное объединение альбома не гарантируется.
- Ответы сопоставляются с местными ID копий. Для отсутствующей связи добавляется короткая текстовая цитата, если исходное событие содержит текст ответа.
- Собственные копии ботов не возвращаются в исходную группу. Повторно полученное событие не создаёт вторую задачу, а одинаковый текст двух разных людей сохраняется как два сообщения.
- Текст сообщения с вложением вне тестового объёма переносится с явной пометкой о непереданном вложении. Сообщения только с таким вложением дают пометку; сами видео/документы/голосовые не переносятся.

## Надёжность и ограничения

Входящее сообщение и курсор фиксируются в SQLite одной транзакцией. Очередь сохраняет порядок по каждому направлению; используется ограничение частоты отправок. Ошибки 429 и `attachment.not.ready` дают отложенный повтор.

С 20.10.2026 некорректные события выбранных групп сохраняются в таблице `quarantine` вместе с причиной. Корректные сообщения пакета продолжают обработку, курсор фиксируется вместе с задачами и карантином. `status` показывает открытые проблемы без содержимого переписки. События посторонних чатов не архивируются. Если невозможно определить чат события, пакет не подтверждается; ошибки базы или программы также откатывают пакет. Позднее восстановление события из карантина может нарушить исходный порядок доставки.

Схема базы версионируется; текущая версия — 3. Перед обновлением старой базы создаётся согласованная SQLite-копия `bridge.sqlite3.v<предыдущая версия>-<случайный суффикс>.bak` с правами 0600 рядом с базой. Копия также содержит данные переписки и остаётся в исключённой из Git `.state/`. Просмотр статуса и очереди открывает базу только для чтения и не выполняет миграций. Результаты доработок — в [протоколе P0](P0-VALIDATION.md).

После тайм-аута или ошибки сервера во время публикации результат может быть неизвестен. Такая задача получает статус `uncertain`, и направление останавливает отправку следующих сообщений до ручной проверки. Автоматический повтор мог бы создать дубль. Аналогично `sending` после аварийного завершения превращается в `uncertain`; `failed` также требует разбора. Абсолютная доставка без дублей при любых сбоях не обещается. Обратное направление может продолжать работу.

Для разбора добавлены `queue list/show/retry/confirm/skip` и `quarantine list/show/retry`. Изменяющие команды выполняются после остановки моста, требуют `--reason` и оставляют запись в `audit`. Повтор `uncertain` дополнительно требует `--accept-duplicate-risk`; найденная копия подтверждается через `--remote-id`. `skip --remaining` пропускает неотправленные части того же сообщения начиная с выбранной. Подробные команды и порядок сверки — в [инструкции оператора](OPERATIONS.md).

`status` показывает процесс, состояния обоих направлений, количество и возраст задач, время успешного опроса и доставки, карантин. `health --json` возвращает тот же снимок и код 0 при нормальном состоянии, 1 при проблеме. Отсутствие новых сообщений не считается сбоем, если пустые опросы API проходят. Для старых задач без времени создания возраст помечается неизвестным, а не вычисляется от момента миграции.

Отдельная команда `monitor` проверяет состояние каждые 30 секунд и выдаёт JSONL-события `problem`/`recovery` только при изменении проблемы. Порог устаревания heartbeat/опроса — 180 секунд, возраста очереди — 300 секунд; параметры настраиваются. Отсутствие работающего процесса выявляется по блокировке при следующей проверке. История наблюдений и очередь оповещений сохраняются в `.state/monitor.sqlite3`, поэтому перезапуск монитора не повторяет уже выданное оповещение об неизменной проблеме. Вывод доступен в stdout или локальный файл; получатель и внешний канал доставки пока не подключены. См. [запуск монитора](OPERATIONS.md#мониторинг).

На 20.10.2026 проходят 51 автоматический тест и отдельный `smoke_p0.py`: временные базы, настоящий CLI и отдельные процессы моста/монитора с подменённым API. Эти автоматизированные проверки не вызывают реальные API и не меняют рабочую `.state`. Последующий живой запуск с миграцией рабочей базы и ручное подтверждение пользователя описаны отдельно в [протоколе 20.10](LIVE-TEST-2026-10-20.md).

Правки, удаления и импорт старого архива в этом прототипе не реализованы. История новичку остаётся штатной возможностью чатов, которую проверяем отдельно. Указатели событий не заменяют архив и не восстанавливают события за пределами хранения платформ.

В `.state/` временно сохраняются тексты, имена, ID и приватные URL картинок для очереди. Это реальные данные теста, не обезличенный журнал. Каталог исключён из Git; не использовать ученическую переписку. Длительное хранение и автоматическая очистка пока не реализованы. В консоль не выводятся токены, тела сообщений, URL скачивания и полные ошибки HTTP.

Медиа MAX принимаются только с HTTPS-доменов платформы/CDN из списка в коде; неизвестный домен требует проверки. TLS-проверка включена. Для MAX предусмотрен `MAX_CA_FILE` в `.env`: дополнительный сертификат загружается только в отдельный SSL-контекст MAX, не меняя системное доверие и контекст Telegram.

Для текущего теста корневой сертификат получен по HTTPS с [официального статического ресурса Госуслуг](https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt) и сохранён в `.state/russian-root-ca.pem`. Subject/issuer: `Russian Trusted Root CA`, срок 01.03.2022–27.02.2032. SHA-256 отпечаток сертификата: `D26D2D0231B7C39F92CC738512BA54103519E4405D68B5BD703E9788CA8ECF31`. Необходимость сертификата указана в [документации MAX](https://dev.max.ru/docs-api). Сертификат не является секретом; проверка имени сервера и цепочки остаётся включённой.

## Проверка на живых группах — базовая выполнена

Подтверждены текст и фото с подписью в обе стороны, ответы в обе стороны и перезапуск без повторной доставки трёх уже отправленных сообщений. Базовый сценарий из 5 исходных сообщений дал 5 копий; обратное направление ответа проверено позже в тот же день. Подробности и непроверенные сценарии — в [протоколе](LIVE-TEST-2026-10-19.md).

Для расширенной проверки 20 исходных текстов (по 10 на каждой площадке) должны дать 20 копий. Затем проверить JPEG/PNG с подписью, ответы на копию, повторное событие, одинаковый текст от двух людей, перезапуск и короткий сбой. Отдельно зафиксировать потери оформления альбомов и неизвестные результаты отправки. Успешные локальные тесты не подтверждают доступы или работу реальных API.

Источники: [Telegram Bot API](https://core.telegram.org/bots/api), [MAX messages](https://dev.max.ru/docs-api/methods/POST/messages), [MAX image upload](https://dev.max.ru/docs-api/use-cases/sending-messages/media), [официальная OpenAPI MAX](https://github.com/max-messenger/api-schema/blob/main/schema.yaml).
