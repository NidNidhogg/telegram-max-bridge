# Требования к размещению моста Telegram ↔ MAX

Дата: 21.10.2026. Документ для администратора сервера заказчика. Соответствие существующей площадки этим требованиям проверяется до переноса.

Сервис синхронизирует общение пользователей в группах Telegram и MAX: сообщения и картинки, отправленные в Telegram, появляются в чате MAX, и наоборот. Администратор группы может через Telegram ответить на вопрос, заданный в MAX, и ответ будет виден пользователям в обеих группах. Видно, кто написал сообщение, в каком чате и откуда пришёл ответ.

## Этап 1. Перенос текущей тестовой версии

На первом этапе на сервер переносится **существующий мост с опросом API**. Цель — проверить круглосуточную работу без ноутбука. Для этого этапа адрес сайта, отдельный домен, входящий порт 443 и настройка webhook **не требуются**.

- **Окружение:** Linux-сервер или Linux-VM с доступом к командной строке, возможностью установить Python 3.11+, зависимости из `uv.lock` и запустить постоянные фоновые службы. Обычный веб-хостинг подходит только при наличии этих возможностей. Предпочтительна Ubuntu Server LTS; на Windows-хосте можно выделить Linux-VM.
- **Ресурсы и диск:** стартовый ориентир — 2 vCPU, 2 ГБ RAM и от 20 ГБ SSD для приложения и данных. Это оценка для первой пары групп, которую следует уточнить по нагрузке и срокам хранения. SQLite хранится на постоянном локальном диске, доступном учётной записи службы.
- **Сеть:** исходящий HTTPS-доступ к Telegram, MAX и узлам загрузки медиа обеих платформ. Нужна проверка DNS и TLS с самого сервера; если сеть использует прокси, фильтрацию или дополнительный корневой сертификат MAX, это согласуется до установки. Входящие подключения извне текущему процессу polling не нужны.
- **Запуск:** выделенная учётная запись с ограниченными правами; служба с автозапуском после перезагрузки и перезапуском после сбоя, отдельная служба монитора. Нужны возможность читать состояние службы и логи, а также назначенный ответственный за оповещения и разбор `failed`/`uncertain`.
- **Доступ и секреты:** настройка через SSH по **публичному** ключу, при необходимости через VPN, либо установка администратором заказчика по инструкции. Закрытый SSH-ключ не передаётся. Токены ботов и файл `.env` передаются вне Git и журналов через согласованный защищённый способ; администраторы сервера потенциально имеют доступ к секретам работающего приложения.
- **Сохранность:** перенести или создать постоянный каталог `.state` и сделать согласованную резервную копию SQLite перед переключением. Для сохранения связей ответов на старые сообщения переносится существующая база. Резервные копии размещаются отдельно от рабочего диска и проверяются восстановлением. Одновременно два экземпляра с теми же ботами работать не должны.

**Результат этапа:** на тестовой паре групп тексты, фото и ответы проходят в обе стороны при выключенном ноутбуке; очередь сохраняется после перезапуска сервера, состояние видно через `health`. Это тестовый запуск: [MAX ограничивает Long Polling разработкой и тестированием](https://dev.max.ru/docs-api/methods/GET/updates).

## Этап 2. Рабочее размещение через webhook

Для рабочего режима потребуется реализовать и проверить приём событий через webhook, затем обеспечить:

- постоянный публичный HTTPS-адрес на порту 443 для двух маршрутов, с доверенным сертификатом, полной цепочкой и автоматическим продлением; существующий reverse proxy сайта может передавать эти маршруты приложению, поэтому отдельный публичный IP для приложения, поддомен и новый домен необязательны;
- доступность маршрутов для Telegram и MAX без браузерной авторизации и CAPTCHA, проверку секретов webhook и запись события в SQLite **до** успешного ответа API;
- мониторинг работы служб, подписок, сертификата и места на диске, внешний канал оповещений, согласованные сроки хранения переписки, правила доступа и удаления, резервное копирование и проверку восстановления.

По [официальным требованиям MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions) webhook использует HTTPS на порту 443 и доверенный сертификат; [Telegram поддерживает webhook](https://core.telegram.org/bots/api#setwebhook). Требования платформ сверены 21.10.2026 и перепроверяются перед переключением. Порядок переноса и критерии готовности приведены в [плане размещения](SERVER-DEPLOYMENT-PLAN.md).
