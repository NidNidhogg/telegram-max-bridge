# Развёртывание и эксплуатация моста Telegram ↔ MAX

Описание сервиса и команды запуска приведены в [README](../../README.md). Здесь описаны требования к серверу, подготовка размещения, диагностика и действия оператора при сбоях доставки.

Docker-поставка одной связки принята в [D1](SERVER-DEPLOYMENT-PLAN.md#приёмка-d1), обработка ошибок API/сети и безопасных повторов — в [D2](SERVER-DEPLOYMENT-PLAN.md#приёмка-d2), сохранность состояния и восстановление — в [D3](SERVER-DEPLOYMENT-PLAN.md#приёмка-d3). Все три задачи слиты в `main`; проверенные версии, результаты и ограничения хранятся в плане. [D4](SERVER-DEPLOYMENT-PLAN.md#постановка-d4) — healthcheck, структурированные логи и диагностика — реализован и передан на независимую приёмку, но ещё не принят; команды и форматы ниже описывают ветку D4.

**Область текущих команд:** одна пара групп Telegram ↔ MAX. Каналы, статус по отдельным связкам и их независимая приостановка ещё не реализованы. Изменяющие команды ниже требуют остановки всего текущего моста. Планируется **добавить поддержку каналов в существующий двусторонний мост**; будущие правила сопровождения перечислены в конце документа и не являются готовыми командами CLI.

На сервере команды выполняются из корня проекта через Docker и Makefile по [README](../../README.md#запуск-в-docker); устанавливать Python и выполнять `uv sync` на хосте не требуется. Примеры `.venv/bin/python` ниже предназначены для локальной разработки после `uv sync --locked`. В Docker использовать `make cli ARGS='<аргументы>'` (например, `make cli ARGS='queue show 12'`); команда работает с выбранным `PROJECT`, база находится в volume `/state`. Для просмотра есть `make status` и `make health`. Изменяющие команды выполнять после `make stop-bridge`, затем `make up`. Просмотр работает без токенов и сетевых запросов. При локальном запуске по умолчанию используется `02-messenger-sync/.state/bridge.sqlite3`; `--state-dir /абсолютный/путь` выбирает отдельный каталог состояния.

Локальный тест 20.10.2026 завершился с `health: ok` и пустой очередью. Этот снимок не показывает текущее состояние после клонирования или переноса. Для работающего процесса проверять `health`, а при запуске службой — также её состояние в системе управления службами.

## Требования к серверу

Соответствие площадки этим требованиям проверяется до переноса. Тестовое размещение относится к текущей одной паре групп; рабочий режим и подключение каналов требуют доработок из [плана](SERVER-DEPLOYMENT-PLAN.md).

### Этап 1. Перенос текущей тестовой версии

На первом этапе на сервер переносится **существующий мост с опросом API для одной пары групп**. Цель — проверить круглосуточную работу без ноутбука. Для этого этапа адрес сайта, отдельный домен, входящий порт 443 и настройка webhook **не требуются**. Для каналов сначала необходимо выполнить доработку и приёмку из плана.

- **Окружение:** Linux-сервер или Linux-VM с доступом к командной строке, Docker Engine, Docker Compose и Make. Развёртывание и эксплуатация выполняются через Makefile по [README](../../README.md#запуск-в-docker); Python и зависимости из `uv.lock` находятся в образе. Обычный веб-хостинг подходит только при наличии этих возможностей. Предпочтительна Ubuntu Server LTS; на Windows-хосте можно выделить Linux-VM. Архитектура сервера подтверждается до переноса; сборку и запуск на ней нужно проверить отдельно.
- **Ресурсы и диск:** предложенные заказчиком 1–2 ГБ — исходный бюджет, который нужно проверить на сервере с учётом Docker-образов, кэша сборки, SQLite, журналов и резервных копий. Достаточность этого объёма для Docker-поставки пока не подтверждена. Предыдущая оценка 20 ГБ была запасом, а не обязательным минимумом. Лимиты CPU/RAM и срок хранения данных уточняются по фактической нагрузке, с учётом работы Битрикс на том же сервере. SQLite хранится в постоянном Docker volume на локальном диске; необходимы контроль размера базы и свободного места. Docker-логи ограничены настройками Compose; автоматическая очистка SQLite и `alerts.jsonl` ещё не реализована.
- **Сеть:** исходящий HTTPS-доступ к Telegram, MAX и узлам загрузки медиа обеих платформ. Нужна проверка DNS и TLS с самого сервера; если сеть использует прокси, фильтрацию или дополнительный корневой сертификат MAX, это согласуется до установки. Входящие подключения извне текущему процессу polling не нужны.
- **Запуск:** учётная запись для развёртывания с согласованными правами на Docker; контейнеры `bridge` и `monitor` запускаются через `make up` без root внутри контейнера (UID/GID `10001:10001`). Нужны постоянный volume с правом записи для этого пользователя, автозапуск Docker после перезагрузки, проверка политики перезапуска из Compose и доступ к `make status`, `make health`, `make logs`. Ответственный за оповещения и разбор `failed`/`uncertain` назначается до подключения.
- **Доступ и секреты:** настройка через SSH по **публичному** ключу, при необходимости через VPN, либо установка администратором заказчика по инструкции. Закрытый SSH-ключ не передаётся. Токены ботов и файл `.env` передаются вне Git и журналов через согласованный защищённый способ; администраторы сервера потенциально имеют доступ к секретам работающего приложения.
- **Сохранность:** подготовить постоянный volume `<project>_state`, смонтированный в `/state`, и сделать согласованную резервную копию SQLite перед переключением. Для сохранения связей ответов на старые сообщения переносится существующая база; процедура переноса локальной `.state` в volume в D1 не автоматизирована. Резервные копии размещаются отдельно от рабочего диска и проверяются восстановлением. Обычный `make down` сохраняет volume; команды резервного копирования и восстановления ещё предстоит добавить. Одновременно два экземпляра с теми же ботами работать не должны.

**Результат этапа:** на тестовой паре групп тексты, фото и ответы проходят в обе стороны при выключенном ноутбуке; очередь сохраняется после перезапуска сервера, состояние видно через `make health`. Это тестовый запуск: [MAX ограничивает Long Polling разработкой и тестированием](https://dev.max.ru/docs-api/methods/GET/updates).

### Этап 2. Рабочее размещение через webhook

Для рабочего режима потребуется реализовать и проверить приём событий через webhook, затем обеспечить:

- постоянный публичный HTTPS-адрес на порту 443 для двух маршрутов, с доверенным сертификатом, полной цепочкой и автоматическим продлением; существующий reverse proxy сайта может передавать эти маршруты приложению, поэтому отдельный публичный IP для приложения, поддомен и новый домен необязательны;
- доступность маршрутов для Telegram и MAX без браузерной авторизации и CAPTCHA, проверку секретов webhook и запись события в SQLite **до** успешного ответа API;
- мониторинг работы служб, подписок, сертификата и места на диске, внешний канал оповещений, согласованные сроки хранения переписки, правила доступа и удаления, резервное копирование и проверку восстановления.

### Доступ для подключения каналов после доработки

- Подготовить перечень связок: проект, Telegram ID, MAX ID, типы «группа» или «канал» и используемые боты. В каждой паре новые публикации должны переноситься в обе стороны; переключение площадки-источника не требуется.
- Предоставить ботам необходимые роли и права для получения и публикации сообщений в каждом канале. Подтвердить их доступность с обеих сторон на пробной паре. Токены хранить в закрытой конфигурации приложения; наличие доступа к Git не даёт доступа к ботам.
- Использовать один сервер для всех согласованных связок. Число обработчиков webhook определяется выбранными ботами, а не количеством каналов; в текущем плане предусмотрены два общих маршрута для одной пары ботов. Отдельный сервер или домен для каждого канала не требуется.
- Назначить ответственного за сверку неопределённых отправок в целевых каналах и предоставить ему доступ к нужным публикациям. Комментарии под постами, перенос истории, синхронизация правок и удалений в этот этап не включены.

По [официальным требованиям MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions) webhook использует HTTPS на порту 443 и доверенный сертификат; [Telegram поддерживает webhook](https://core.telegram.org/bots/api#setwebhook). Требования платформ сверены 21.10.2026 и перепроверяются перед переключением. Порядок переноса и критерии готовности приведены в [плане размещения](SERVER-DEPLOYMENT-PLAN.md).

## Просмотр

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py status
.venv/bin/python 02-messenger-sync/poc/bridge.py queue list --limit 100
.venv/bin/python 02-messenger-sync/poc/bridge.py queue show 12
.venv/bin/python 02-messenger-sync/poc/bridge.py quarantine list
.venv/bin/python 02-messenger-sync/poc/bridge.py quarantine show 3
```

Команды `list` показывают первые записи по ID в пределах лимита; `show` — метаданные выбранной записи. Текст сообщения, исходное событие, приватные URL и причины ручных действий из аудита в обычный вывод не включаются. `queue show` показывает связанные части и историю состояний. Просмотр можно выполнять при работающем мосте; он не мигрирует базу.

## Перед изменением

Остановить мост через Ctrl+C или SIGTERM (в Docker — `make stop-bridge` или `make down`) и дождаться завершения: async-версия даёт активным запросам до 30 секунд, затем отменяет их с сохранением `uncertain` при возможной публикации. Не освобождать блокировку и не запускать второй экземпляр, пока первый не завершился. Изменяющая команда использует ту же исключительную блокировку, что `run`, и откажет при работающем процессе. После аварии оставшийся `sending` преобразуется в `uncertain` перед разбором.

Каждое действие требует непустой `--reason` длиной не более 1000 символов. Причина и переход состояния сохраняются в `audit` атомарно с действием; не записывать туда секреты или переписку.

## Определённый отказ: failed

Устранить причину отказа, затем вернуть задачу в ожидание:

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py queue retry 12 --reason 'Причина отказа устранена'
```

Команда не отправляет сообщение сама. Отправка выполняется после следующего `run`. Повтор команды для уже ожидающей задачи ничего не меняет.

## Неизвестный результат: uncertain

Сверить целевую группу с исходным сообщением. Если копия найдена, записать её ID:

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py queue confirm 12 --remote-id mid.example --reason 'Копия найдена в целевой группе'
```

Для копии в Telegram нужен положительный числовой ID. Подтверждение восстанавливает связь для ответов. Повтор подтверждения с тем же ID безопасен; другой ID для уже доставленной задачи отклоняется. ID, занятый другой задачей того же направления, также отклоняется.

Если принято решение повторить неопределённую отправку:

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py queue retry 12 --accept-duplicate-risk --reason 'После сверки принято решение о повторе'
```

Повтор может создать дубль, если первая публикация всё-таки состоялась. Флаг фиксирует осознанное решение; программа не утверждает, что копии нет.

## Явный пропуск

Пропустить одну задачу либо все ещё неотправленные части того же сообщения начиная с неё:

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py queue skip 12 --reason 'Доставка отменена ответственным'
.venv/bin/python 02-messenger-sync/poc/bridge.py queue skip 12 --remaining --reason 'Оставшиеся части сообщения отменены'
```

`skipped` не блокирует следующие сообщения. Уже отправленные части сохраняются, части других сообщений не затрагиваются. Пропуск одного фрагмента без `--remaining` оставляет остальные фрагменты в очереди.

## Карантин входных событий

После исправления обработчика повторно разобрать сохранённое событие:

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py quarantine retry 3 --reason 'Обработчик исправлен и проверен'
```

Команда использует сохранённую привязку ботов и чатов. Если ошибка остаётся, событие сохраняет состояние `open`, причина и счётчик попыток обновляются. При успехе оно становится `resolved`, задачи появляются в очереди без перемещения курсора. Повтор для `resolved` ничего не добавляет. Восстановленное сообщение может быть доставлено после более новых.

## Возобновление

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py status
.venv/bin/python 02-messenger-sync/poc/bridge.py run
```

Перед миграцией создаётся резервная копия предыдущей схемы рядом с базой с правами 0600. Не заменять рабочую базу старой копией при запущенном процессе: откат состояния может привести к повтору уже опубликованных сообщений.

## Мониторинг

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py status --json
.venv/bin/python 02-messenger-sync/poc/bridge.py health --json
```

`status` возвращает код 0, если удалось сформировать вывод; смотреть поле `ok`. `health` возвращает код 0 при `ok=true`, 1 при проблеме. Ошибка аргументов CLI даёт код 2. Эти команды читают локальное состояние и не обращаются к API. При отсутствии или недоступности базы `health` возвращает JSON с причиной `state_missing` или `state_unavailable`.

Снимок содержит состояние процесса и heartbeat, время успешного опроса и доставки каждой платформы, количества задач по состояниям, возраст самой старой ожидающей/незавершённой задачи, первую незавершённую задачу и число открытых проблем входных событий. Пустая очередь при успешных опросах считается исправной; отсутствие успешной отправки в пустой группе само по себе не является ошибкой.

При `make up` в Docker монитор запускается отдельным сервисом `monitor` с тем же volume и пишет в `/state/alerts.jsonl`; healthcheck сервиса `bridge` использует `health --json`. Пороги задаются общими `HEALTH_STALE_AFTER` и `HEALTH_QUEUE_AGE` по [README](../../README.md#запуск-в-docker). Healthcheck не перезапускает зависший процесс автоматически; внешние оповещения и резервное восстановление остаются следующими задачами. Без Docker для непрерывного наблюдения запустить **отдельный процесс**, пока мост работает в другом терминале:

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py monitor --interval 30 --stale-after 180 --queue-age 300 --alerts-file 02-messenger-sync/.state/alerts.jsonl
```

Один проход для внешнего планировщика:

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py monitor --once
```

Без `--alerts-file` события пишутся в stdout, по одному JSON-объекту на строку. При неизменном состоянии вывода нет. Все запуски одного монитора должны использовать один и тот же каталог состояния и один выбранный канал вывода: отметка о выдаче относится к событию, а не к каждому возможному файлу/получателю. Уже выданные события не переигрываются при смене канала.

Параметры в секундах: `--interval` — частота проверки (по умолчанию 30, положительное число до 60), `--stale-after` — порог устаревания heartbeat/успешного опроса (180), `--queue-age` — порог возраста незавершённой очереди (300). При старте процессу даётся `stale-after` на первый успешный опрос; зафиксированная ошибка API видна сразу. Процесс, не удерживающий блокировку, считается остановленным независимо от свежести последнего heartbeat. Фактическое оповещение появляется при следующем проходе монитора.

Основные коды проблем:

| Код | Что проверить |
|---|---|
| `process_stopped` | Работает ли `run`; при намеренной остановке это ожидаемый сигнал |
| `heartbeat_stale` | Не завис ли процесс или сетевой запрос |
| `poll_error` / `poll_stale` | Доступность API, права бота и последний успешный опрос |
| `delivery_blocked` | Задачу из `job_id` через `queue show` |
| `queue_too_old` | Очередь, ограничения отправки и доступность целевой площадки |
| `queue_age_unknown` | Старые задачи без времени создания; оценить их вручную |
| `input_quarantine` | Событие из `first_id` через `quarantine show` |
| `migration_required` | Остановить процесс и запустить обновлённую версию для миграции |
| `state_missing` / `state_unavailable` | Каталог состояния, доступ к базе и её целостность |

Событие имеет `event_id`, `kind` (`problem` или `recovery`), время обнаружения и метаданные проблемы. Состояние наблюдений и невыданные события сохраняются в `monitor.sqlite3`; отдельный `monitor.lock` исключает параллельные мониторы. Изменение блокирующей задачи или количества проблем считается новым значимым состоянием. При недоступной базе ранее известные проблемы не объявляются восстановленными до успешного чтения.

Ошибка записи JSONL оставляет событие в очереди; после исправления вывода запустить монитор повторно. Авария после записи строки, но до фиксации отметки может дать повтор с тем же `event_id`, поэтому внешний обработчик должен удалять такие повторы. Внешний получатель и канал доставки ещё не подключены. Для обнаружения остановки самого монитора и постоянной работы потребуется служба/внешний контроль на этапе P1.2.

Существующий процесс старой версии нужно перезапустить обновлённым кодом, чтобы он начал записывать телеметрию. В старых задачах неизвестный возраст сохраняется как неизвестный; миграция не придумывает время получения сообщения. Схема версии 3, резервные копии, аудит и данные монитора остаются в `.state`; автоматическая очистка относится к P1.3.

### Коды диагностики и действия

Проверка — `make status` (кратко) или `make cli ARGS='health --json'`; задача — `make cli ARGS='queue show <job_id>'`. Изменяющие команды — после `make stop-bridge`.

| Код / симптом | Проверка | Действие |
|---|---|---|
| нет `issues`, нет доставок | `make status`: `poll=ok`, `last_poll` свежий | Тихий чат — норма, ничего не делать |
| голова `wait=retry`, `reason` `connect_failed`/`transport_error`/`server_error` | `retry_at` в `make status`, `queue show` | Ждать срок; при долгом ожидании проверить сеть/DNS до платформы |
| голова `reason=rate_limited` с далёким `retry_at` | `queue show <job_id>`: `ready` | Ждать: срок сервера соблюдается целиком; не перезапускать ради ускорения |
| `platform_paused` (`auth_rejected`/`tls_failed`) | `make status`, логи `platform_paused` | Пауза держится до перезапуска процесса: исправить токен/права бота или `MAX_CA_FILE`, затем `make stop-bridge`, проверить `make cli ARGS='queue list'` (`uncertain` сверить по разделу ниже, без слепого повтора) и `make up` |
| `worker_stalled` (worker, фаза) при свежем heartbeat | `make status`: `worker …: state=stalled` | Собрать `make logs`, затем `make stop-bridge` и `make up`; `uncertain` после этого сверять по разделу ниже |
| `delivery_blocked` `failed` / `uncertain` | `queue show <job_id>` | `failed`: устранить причину и `queue retry`; `uncertain`: сверка, `queue confirm` или `skip`; без слепого повтора |
| `state_unavailable` / `stopped_with_error` `storage_error` | `make status`, `make logs` | Проверить место и права volume; базу и volume не удалять |

Логи `make logs` (stdout/stderr контейнеров `bridge` и `monitor`, ротация Docker) — JSON Lines с `run_id` в каждой записи, без токенов, текстов, имён, URL и тел ответов; искать по `event`, `job_id`, `direction`, `error_code`. Оповещения `monitor` пишутся в `/state/alerts.jsonl` (прежние поля `event_id`, `kind`, `detected_at`, `issue` плюс `timestamp`, `level`, `component`, `event`, `run_id`); восстановление фиксируется после второго подряд чистого наблюдения, одна причина не повторяется на каждом цикле, при сбое записи событие выдаётся позже с тем же `event_id`.

## Ошибки async-получателей

При временном сбое получатель повторяет опрос с задержкой 2, 4, 8 … 30 секунд с разбросом +0–20 %. Если сервер указал Telegram `retry_after` или HTTP `Retry-After`, повтор не начнётся раньше этого срока; после успешного опроса задержка снова начинается с 2 секунд. Во время ожидания другой получатель, независимый отправитель и heartbeat продолжаются. При 401/403 или ошибке проверки TLS-сертификата опроса платформа приостанавливается до проверки токена, прав или `MAX_CA_FILE` и перезапуска; проверка TLS не отключается; исправность heartbeat сама по себе не означает исправность этой платформы. Проверить `health --json` и время успешного опроса. 409 означает конфликт poller и остановку всего моста: найти второй экземпляр перед перезапуском. Ошибка SQLite или программы также останавливает процесс; не повторять неопределённые отправки без сверки. Если запись пакета не удалась (например, нет места), курсор не сдвигается: после освобождения места и перезапуска платформа отдаст события снова, дубли не создаются. Сообщение `SQLite не включил WAL и synchronous=FULL` или ошибка открытия базы останавливают запуск; файл базы не удалять и не заменять — сохранить копию volume и разобрать причину (права, файловая система, повреждение). После аварийного завершения lock-файл не удалять: блокировку снимает ОС.

## Ошибки доставки

Очередь направления ждёт, пока задача стоит в `pending` со сроком повтора: колонка `ready` в `make cli ARGS='queue list'`, причина в `error`.
- **Отказ соединения** (`Соединение не установлено; запрос не отправлен`), **`429`** и **временный сбой скачивания фото** (сеть, HTTP 429 или 5xx) повторяются автоматически. Задержка растёт до 120 секунд, а срок повтора, указанный сервером, соблюдается. Если ожидание длится долго, проверить сеть и DNS до соответствующей платформы. Перезапуск и пересоздание контейнера срок повтора не сбрасывают.
- **`failed`** означает постоянный отказ: 401/403, ошибку запроса 4xx, отказ 4xx при скачивании фото (например, 404), ошибку TLS-сертификата или неподдерживаемое фото. Устранить причину, остановить мост и выполнить `queue retry`.
- **`uncertain`** после HTTP 5xx (независимо от кода в теле ответа), таймаута или обрыва ответа во время публикации автоматически не повторяется, в том числе после перезапуска. Сверку выполнять по разделу [uncertain](#неизвестный-результат-uncertain).

## Запланированная эксплуатация каналов и нескольких связок

Раздел описывает требования к будущей версии по [плану доработки](SERVER-DEPLOYMENT-PLAN.md#план-доработок). Заказчик указал три канала и пять групп; до подключения нужно сверить список обеих сторон каждой пары и принадлежность проекту.

- Перед подключением канала проверить ID обеих сторон, типы чатов и права ботов на получение публикаций и отправку копий. Для пробной пары подтвердить новый текст и фото из Telegram в MAX и из MAX в Telegram без смены режима и возврата копии назад. Подключение каналов текущими `discover`/`bind`/`doctor` ещё не поддерживается.
- В статусе и оповещениях показывать проект, связку, исходную и целевую площадки, соответствующие чаты и блокирующую задачу. Предусмотреть приостановку отдельной связки с сохранением очереди; ошибку доступа конкретного канала и `uncertain` его направления отделить от состояния остальных связок. Отказ всего API или токена может затронуть все использующие его связки.
- При ручной сверке `uncertain` искать копию именно в целевом канале указанной связки. Публикация может выглядеть как пост от имени канала; личного автора нельзя считать обязательным признаком. Подтверждать точный ID найденной копии, а повтор выполнять только после явного решения с учётом риска дубля. Автоматический повтор остаётся запрещённым.
- Контролировать потерю прав публикации, удаление бота и состояние webhook-подписок. Отсутствие новых публикаций в тихом канале само по себе не считать аварией. Проверку доступности приёма и подписок потребуется реализовать вместе с webhook.
- Сохранять конфигурацию связок вместе с согласованной резервной копией базы. При восстановлении проверять назначения задач и связи сообщений до включения отправки; идентификаторы из разных каналов не должны смешиваться. Сроки хранения содержимого, связей и защиты от дублей определить отдельно; нерешённые задачи не удалять автоматически.

Комментарии под постами, синхронизация правок и удалений, перенос старого архива в этот этап не входят. Наличие бота в канале и обновлённого плана не означает, что канал уже подключён или прошёл приёмку.
