# План внедрения асинхронного выполнения Telegram ↔ MAX

Пользовательское назначение сохраняется по [основному описанию сервиса](SERVICE-DESCRIPTION.md): сообщения и картинки передаются в обе стороны, администратор может отвечать из Telegram на вопросы из MAX, автор и исходная площадка видны участникам.

Дата: 20.10.2026. Статус: **A0–A4 выполнены; A5 выполнен частично, тест остановлен по просьбе пользователя**. Async-код P1.1 [общего плана](IMPLEMENTATION-PLAN.md) внедрён и работает на тестовой паре; полная приёмка ещё не закрыта. Фактические результаты — в [протоколе асинхронности](poc/ASYNC-VALIDATION.md) и [живом протоколе](poc/LIVE-ASYNC-TEST-2026-10-20.md).

Решение: сохранить наше ядро, правила API и SQLite; заменить блокирующие сетевые вызовы на `aiohttp`, организовать выполнение через `asyncio`. Внедрение aiogram/maxapi отложено и не является условием этого этапа. Webhook и размещение на сервере остаются отдельным P1.2.

Исходная точка кода — `1f31580`, схема SQLite 3. Ранее пройдены 51 тест и `smoke_p0.py`, пользователь подтвердил живой обмен; [результаты P0](poc/P0-VALIDATION.md), [живой тест](poc/LIVE-TEST-2026-10-20.md). Это результаты прежней версии, а не проверка будущего async-кода.

Порядок: **A0 → A1 → A2 → A3 → A4 → A5**. После каждого изменения кода: целевые тесты → полный регрессионный набор → отдельный запуск новой версии на временной базе → обновление документации → отдельный коммит. Провал критерия готовности останавливает переход к следующему этапу.

## Целевое выполнение

Один процесс, один event loop, пять контролируемых задач:

| Задача | Ответственность |
|---|---|
| Получатель Telegram | Опрос, обработка пакета, фиксация offset вместе с задачами/карантином |
| Получатель MAX | Опрос, обработка пакета, фиксация marker вместе с задачами/карантином |
| Отправитель в Telegram | Подготовка вложения, последовательная публикация, результат и reply-связь |
| Отправитель в MAX | То же для MAX, со своими ограничениями частоты |
| Heartbeat | Состояние процесса независимо от ожиданий сети |

Постоянные HTTP-сессии и пулы соединений создаются на запуск и закрываются при завершении. TLS Telegram использует стандартное доверие; дополнительный сертификат MAX остаётся ограничен MAX. Заголовок Authorization задаётся для конкретного API-запроса и не передаётся файловым хостам.

По одному получателю на платформу и одному отправителю на направление. Параллельных отправок внутри направления нет; `failed`/`uncertain` по-прежнему блокируют последующие задачи этого направления. Сбой MAX может задержать Telegram-фото, которое ещё надо скачать из MAX; независимость относится к операциям, которым отказавшая платформа не нужна.

SQLite остаётся в одном потоке: короткие синхронные операции, без `await` внутри транзакций. `asyncio.Queue` может быть только сигналом пробуждения, если он понадобится; источником истины остаётся SQLite. Отдельный монитор P0 продолжает работать своим процессом.

## A1. Отделить сетевые ожидания от транзакций

**Изменения.** В `poc/bridge.py` выделить минимальные границы вокруг `Api.request/download/prepare_photo`, `Bridge.poll/deliver` и цикла запуска. Сохранить существующую реализацию HTTP на этом шаге: сначала проверить извлечение без смены поведения.

Отдельно обозначить три фазы отправки:

1. Выбрать следующую допустимую задачу и подготовить вложение без публикации сообщения.
2. Повторно проверить допустимость задачи и зафиксировать `sending` короткой атомарной операцией **до** запроса публикации.
3. Выполнить запрос и записать результат с ID копии.

Во время подготовки задачу не берёт второй отправитель: на направление создаётся ровно один worker. Между проверкой перед публикацией и commit `sending` не должно быть `await`. Изменение оператором по-прежнему запрещено при занятой процессной блокировке.

Не менять сериализацию payload, схему 3, ID, курсоры, нормализацию, формат сообщений и семантику операторских команд. Извлекать только необходимый код; общий рефакторинг модулей здесь не требуется.

**Проверки.** Регрессия P0 и отдельный сквозной запуск. Проверить чтение старой базы, сохранение reply-связей, атомарность задач/карантина/курсора и прежнее поведение неопределённой отправки.

**Документы.** Обновить `HOW-IT-WORKS.md`, записать результаты A1.

**Готово:** сетевой транспорт и транзакции имеют явные границы, поведение прежнее.

## A2. Реализовать неблокирующий HTTP-транспорт

**Изменения.** Перенести сетевые методы на `async def` и `aiohttp`. Сохранить используемые endpoint, параметры, сырые JSON-события и контролируемые ошибки `ApiError/TransportError`. Не добавлять строгую типизацию входного пакета, которая может остановить карантин одного некорректного элемента.

Первоначальные ориентиры, которые нужно проверить на стенде: connect timeout 5 секунд, ожидание чтения 20 секунд, общий предел запроса 25 секунд. Отдельно задать пределы пула соединений, чтобы загрузка фото не занимала все соединения для опроса. Long polling пока не включать: сохранить `timeout=0` и явный интервал опроса.

Сохранить потоковые ограничения: JSON API до 2 MiB, фото до 10 MiB, проверка сигнатуры JPEG/PNG/WEBP. Проверять каждый разрешённый переход при скачивании; для API и POST-загрузок автоматические redirect отключить. Существующие ограничения URL, TLS и удаления токена из ошибок обязательны. Не полагаться только на удаление заголовка клиентом при смене хоста.

Автоматические повторы публикации не добавлять. Проверить поведение выбранной версии клиента на сбое повторно используемого соединения, таймауте и 5xx. Перехватывать ожидаемые сетевые ошибки; `CancelledError` не превращать в обычный отказ API. Старый транспорт допустим только как переходный код до A3, без автоматического fallback после ошибки публикации.

**Проверки.** Настоящий HTTP-клиент на локальном стенде: JSON, фото и multipart, медленное чтение, разрыв ответа, 429/403/5xx, лимиты тела, TLS-настройки и redirect. После принятого POST с потерянным ответом сервер наблюдает ровно одну попытку. Проверить закрытие ответов и сессий без утечек.

**Документы.** Обновить описание транспорта и окружения; записать отличия от прежнего клиента и результаты A2.

**Готово:** async-транспорт воспроизводит прежние контракты и ограничения, скрытых повторов публикации нет.

## A3. Подключить независимые обработчики и безопасную остановку

**Изменения.** Подключить async-транспорт к `Bridge` и заменить последовательный цикл пятью задачами. Для сетевых CLI-команд `doctor/discover/run` использовать один `asyncio.run` на команду и явное время жизни клиентов. Команды просмотра/обслуживания SQLite остаются локальными и не открывают HTTP-сессии.

Ожидания интервала, лимита отправки и повторного опроса выполнять через прерываемые async-ожидания. Для одного и того же poller не запускать второй запрос, пока первый не завершён; offset/marker брать только из зафиксированного состояния. У каждого отправителя свои `next_send`, порядок и задержки. Текущие интервалы отправки сохраняются.

Ожидаемые ошибки сети обрабатывать внутри worker: ограниченный backoff опроса и запись проблемы платформы. 401/403 требуют отдельной диагностики области отказа и прекращения затронутых операций, а не бесконечного частого повтора; доступные независимые операции могут продолжаться. Конфликт poller/другого экземпляра требует остановки для защиты связки. Ошибка SQLite или неожиданная ошибка программы останавливает процесс с сохранением незавершённых состояний; её нельзя маскировать как временный сетевой сбой.

При SIGINT/SIGTERM запретить получение новых пакетов и новых задач отправки. Уже полученный пакет либо целиком фиксируется, либо его курсор не продвигается. Активным публикациям дать ограниченное время завершиться; стартовый ориентир shutdown — 30 секунд. После дедлайна отменить оставшиеся задачи, дождаться завершения обработчиков, закрыть сессии, затем базу и процессную блокировку. Не оставлять фоновые сетевые вызовы после освобождения блокировки.

| Момент сбоя/отмены | Состояние и действие |
|---|---|
| До начала публикации, включая скачивание/загрузку вложения | Задача остаётся `pending`, возможен безопасный повтор подготовки |
| После commit `sending`, пока нет определённого результата | `uncertain`; при жёстком падении остаётся `sending`, которое `recover()` переводит в `uncertain` |
| Определённый отказ 429 / `attachment.not.ready` | `pending` с записанной задержкой |
| Другой определённый отказ API | `failed` по действующим правилам |
| Успех с ID копии, commit результата завершён | `sent`, связь для ответов сохранена |

Отмена сама по себе не является доказательством отсутствия публикации. Если ответ потерян или результат не удалось сохранить, не возвращать задачу автоматически в `pending`.

**Проверки.** Управляемо удерживать запрос MAX и одновременно доказать продвижение независимого опроса Telegram и готовой текстовой отправки в Telegram; повторить симметрично. Проверить порядок частей и задач, отсутствие двойного захвата, SIGTERM и аварии по всем фазам таблицы. Полный unittest и адаптированный сквозной прогон должны запускать уже новый runtime.

**Документы.** Обновить запуск, остановку и восстановление в `poc/README.md`, `HOW-IT-WORKS.md`, `OPERATIONS.md`; записать A3.

**Готово:** независимость направлений доказана, остановка сохраняет очередь, временный синхронный runtime удалён.

## A4. Проверить диагностику, нагрузку и длительные сбои

**Изменения.** Heartbeat обновлять отдельной задачей; начальный интервал 2 секунды. Он показывает жизнь event loop, а не исправность каждого worker: ошибки и время успешного опроса/доставки сохраняются по платформам. Не очищать ошибку опроса только потому, что другой worker работает. Отдельный monitor продолжает видеть очередь и сбои через SQLite.

Проверить, что работа с SQLite не создаёт длительных блокировок event loop. Задать короткое ограниченное ожидание блокировки базы; при повторной попытке освобождать транзакцию и ждать асинхронно. Не повторять сетевую публикацию из-за ошибки записи результата. Если измерения покажут неприемлемую блокировку диска, отдельно решить вопрос единственного DB-worker; перенос базы и новый брокер заранее не добавлять.

Задачи runtime фиксированы, новые сообщения увеличивают устойчивую очередь, а не число корутин. Ограничить размер ответа, изображения, число одновременных сетевых операций и частоту сообщений об одинаковой ошибке. Измерить память и задержки на синтетическом потоке, сохраняя исходные лимиты отправки.

**Проверки.** Пятиминутный отказ одного API; работа и восстановление другого направления; heartbeat и monitor во время сетевых ожиданий; 429 с большой задержкой без остановки других worker; недоступная/занятая SQLite; очередь из 100 текстовых задач в каждую сторону и ограниченный набор фото. Проверить одну первичную тревогу и восстановление, отсутствие токенов/текстов/приватных URL в выводе.

При контролируемом зависании сети независимая операция на стенде должна завершиться, пока зависший запрос ещё удерживается; heartbeat — продолжать обновляться. Зафиксировать фактические задержки и потребление памяти. Абсолютные нормативы задержки рабочего пилота согласуются отдельно и учитывают лимиты платформ.

**Документы.** Записать измерения и границы доказательства в `ASYNC-VALIDATION.md`, актуализировать параметры `health/monitor` в инструкции оператора.

**Готово:** медленная сеть не маскирует остановку worker, ресурсы ограничены, диагностика сохраняет смысл P0.

## Откат

Схему 3 и формат задач сохраняем; изменение схемы, если потребуется, выносится в отдельный шаг с миграцией и проверкой совместимости. Перед каждым переключением есть коммит кода, воспроизводимое окружение и согласованная копия состояния.

При проблеме остановить новый процесс, проверить актуальные задачи и `uncertain`, запустить предыдущий релиз с **актуальной совместимой базой**. Автоматически восстанавливать старый backup после новых публикаций нельзя: он может снова поставить уже отправленные сообщения в очередь. Если база стала несовместимой или повреждена, сначала выполнить отдельную сверку и восстановление.

Этот план сохраняет тестовый polling. Переход на webhook, публичный HTTPS, службы сервера, хранение/резервирование и полноценный пилот не считаются выполненными после асинхронности.
