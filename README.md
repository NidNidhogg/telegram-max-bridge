# Telegram ↔ MAX bridge

Локальный мост между одной парой закрытых тестовых групп Telegram и MAX. Переносит новые тексты, фотографии с подписями и ответы от имени двух отдельных ботов с указанием автора и исходной площадки.

**Статус на 20.10.2026:** P0.1–P0.3 реализованы; async-runtime на `asyncio/aiohttp` прошёл 81 тест, локальные сквозные прогоны и 300-секундный отказ MAX. Новая версия работает на прежних тестовых ботах; пользователь подтвердил «Всё работает». Дополнительный живой тест подтвердил 44 доставки: по 20 текстов, одному фото с подписью и одному ответу в каждом направлении. На итоговом снимке `health: ok`, очередь пуста. Тест остановлен по просьбе пользователя, мост оставлен работающим. Расширенная матрица A5 выполнена частично; серверное размещение, webhook и внешний канал оповещений пока не настроены.

## Возможности

- Два направления Telegram ↔ MAX; новые тексты, JPEG/PNG/WEBP и ответы.
- SQLite-очередь с сохранением курсоров, дедупликацией событий и защитой от циклов.
- Карантин некорректных событий выбранных групп без блокировки корректных сообщений пакета.
- Ручной разбор `failed`/`uncertain`, подтверждение копии, явный пропуск и аудит решений.
- Состояние процесса и очереди, `health --json`, отдельный монитор событий `problem`/`recovery` в stdout/JSONL.

Правки, удаления, импорт старого архива, другие вложения, VK и несколько пар групп в текущую реализацию не входят. При неопределённом результате отправки требуется ручная сверка; абсолютная доставка без дублей при любых сбоях не гарантируется.

## Проверки без токенов

Python 3.11+ на macOS/Linux. Async-runtime и HTTP-тесты используют зафиксированный `aiohttp`; окружение воспроизводится через `uv sync --locked`. Aiogram/maxapi не подключены. RTK в примерах — локальная обёртка команд; без неё можно убрать `rtk proxy`.

```sh
rtk proxy uv sync --locked
rtk proxy uv run --locked python -m unittest discover -s 02-messenger-sync/poc -p 'test_*.py' -v
rtk proxy uv run --locked python 02-messenger-sync/poc/smoke_p0.py
rtk proxy uv run --locked python 02-messenger-sync/poc/smoke_async.py
```

Сквозные прогоны используют временные базы, настоящий CLI, отдельные процессы и локальные HTTP-стенды/подменённые API. Они не обращаются к Telegram/MAX и не изменяют рабочую очередь. HTTP-тестам нужно разрешение на локальный listener.

## Подключение собственных тестовых ботов

1. Создать локальный `02-messenger-sync/.env` по образцу [`.env.example`](02-messenger-sync/.env.example), задать права 0600. Заполнить отдельные тестовые токены и заменить ожидаемые имена ботов на собственные.
2. Если дополнительный сертификат MAX не используется, оставить `MAX_CA_FILE` пустым. Если он требуется, установить доверенный сертификат локально и указать его путь; файл доверия из текущего окружения в репозиторий не включён.
3. Подготовить две закрытые тестовые группы и права ботов; выполнить `doctor`, `discover`, `bind`, затем `run` по [инструкции запуска](02-messenger-sync/poc/README.md).
4. Запустить отдельный `monitor`, если нужно локально фиксировать сбои и восстановление; команды — в [инструкции оператора](02-messenger-sync/poc/OPERATIONS.md).

Токены, переписка, SQLite-базы, резервные копии, PID-файлы и логи остаются локально в `.env`/`.state` и исключены из Git. После клонирования репозитория работающий мост и его состояние автоматически не появляются.
