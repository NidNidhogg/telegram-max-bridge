# Мост Telegram ↔ MAX

Сервис синхронизирует общение пользователей в группах Telegram и MAX: сообщения и картинки, отправленные в Telegram, появляются в чате MAX, и наоборот. Администратор группы может через Telegram ответить на вопрос, заданный в MAX, и ответ будет виден пользователям в обеих группах. Видно, кто написал сообщение, в каком чате и откуда пришёл ответ.

Это согласованное с владельцем проекта описание сервиса. Подробности реализации и её текущие границы приведены ниже.

## Что делает текущая версия

Мост переносит новые тексты, фотографии JPEG/PNG/WEBP до 10 МиБ и ответы между **одной заранее выбранной парой групп**. Копия публикуется ботом с подписью автора и исходной площадки. Связи ответов, очередь, указатели получения и защита от повторного получения хранятся в SQLite. Неопределённая публикация получает статус `uncertain`: соответствующее направление ждёт решения оператора и не повторяет отправку автоматически.

Каналы, несколько пар групп, правки, удаления, старый архив, видео, файлы и голосовые пока не поддерживаются. Текущий код принимает только групповые сообщения и отклоняет каналы при проверке подключения. Приём через polling предназначен для тестирования; для рабочего размещения на сервере заказчика требуется webhook. Подробнее — в [описании работы](02-messenger-sync/poc/HOW-IT-WORKS.md) и [плане доработки и размещения](02-messenger-sync/poc/SERVER-DEPLOYMENT-PLAN.md).

## Запуск в Docker

Нужны Docker Engine с Compose v2 и `make`; Python на сервере не нужен. Команды выполняются из корня репозитория. Образ собирается по `uv.lock`, работает под пользователем `10001` без root, с файловой системой только для чтения, без опубликованных портов и повышенных прав.

| Команда | Действие |
|---|---|
| `make build` | Собрать образ `telegram-max-bridge:local` |
| `make up` | Запустить сервисы `bridge` и `monitor` и дождаться healthcheck |
| `make down` | Остановить сервисы; volume с состоянием сохраняется |
| `make update` | Сначала собрать новый образ; при ошибке сборки работающая версия не трогается. Затем пересоздать сервисы |
| `make logs` | Последние логи (`FOLLOW=1` — слежение) |
| `make status` | Состояние контейнеров и `bridge.py status` |
| `make health` | `bridge.py health`: код 1 при проблеме |
| `make test` | Unit-тесты в контейнере без сети и без секретов |
| `make smoke` | `smoke_p0.py` и `smoke_async.py` в контейнере, проверка защиты стенда, затем контейнерный стенд |
| `make doctor` | Проверить ботов, webhook и права в группах |
| `make discover` | Показать ID групп за `DISCOVER_SECONDS` (по умолчанию 90); `bridge` должен быть остановлен |
| `make stop-bridge` | Остановить только `bridge` перед изменяющими командами; `make up` запускает его снова |
| `make cli ARGS='...'` | Любая команда `bridge.py` в выбранном проекте, например `ARGS='queue list'` |
| `make maintenance` | Предпросмотр одного пакета очистки двух БД без записи и API |
| `make maintenance APPLY=1` | Применить один пакет при остановленных bridge и monitor |
| `make compact` | Явное обслуживание и уплотнение двух БД при остановленных сервисах и достаточном месте |

Все цели работают с проектом Compose `telegram-max-bridge` (`PROJECT=...` выбирает другой; передавать одно и то же значение всем командам окружения). Состояние хранится в именованном volume `<project>_state`, смонтированном в `/state`; `make down`, `make update` и пересоздание контейнеров его не удаляют. Не запускать `docker compose down -v` для рабочего проекта: это удаляет очередь и связи ответов.

**Конфигурация.** Compose передаёт в контейнер переменные из `02-messenger-sync/.env` (файл необязателен), заданные в `.env.example`. Переменные окружения процесса имеют приоритет над строками локального `.env`. Пустое или отсутствующее обязательное значение (`TG_BOT_TOKEN`, `MAX_BOT_TOKEN`, а для `run` — `TG_CHAT_ID`, `MAX_CHAT_ID`) останавливает запуск с сообщением без вывода значений. `BRIDGE_STATE_DIR` задаёт каталог состояния; в образе это `/state`. `MAX_CA_FILE` внутри контейнера указывается абсолютным путём к файлу, смонтированному в контейнер, например через локальный `compose.override.yaml`: `services: {bridge: {volumes: [./max-ca.pem:/run/certs/max-ca.pem:ro]}}` и `MAX_CA_FILE=/run/certs/max-ca.pem`. Если дополнительный сертификат не нужен, оставить `MAX_CA_FILE=` пустым. Значение из образца `.state/...` в контейнере не существует и отклоняется проверкой.

Перед первым запуском при остановленном `bridge` выполнить `make doctor`, затем `make discover`. `bind` пишет в локальный `.env` и в контейнере недоступен: найденные `discover` ID групп вписать в `02-messenger-sync/.env` вручную. Перенос существующей локальной `.state` в volume и резервное копирование в D1 не автоматизированы.

Healthcheck контейнера `bridge` вызывает `bridge.py health --json` каждые 30 секунд. Пороги `HEALTH_STALE_AFTER` (180 с) и `HEALTH_QUEUE_AGE` (300 с) задаются переменной окружения или аргументом `make`; Makefile передаёт одни и те же значения healthcheck, `monitor`, `make health` и `make status`. После их изменения нужен `make update`, чтобы healthcheck и monitor получили новые значения. Контейнер становится `unhealthy` при устаревшем heartbeat, ошибке опроса, блокирующей задаче (`uncertain`, `failed`) и слишком старой очереди, даже если процесс жив. Docker сам не перезапускает `unhealthy` контейнер; сигнал разбирает оператор. Сервис `monitor` работает отдельно, видит тот же volume и пишет события в `/state/alerts.jsonl`. При остановке через `make stop-bridge` или `make down` приложение получает SIGTERM через `init`; Compose ждёт до 60 секунд, что больше 30-секундного окна штатного завершения моста.

Контейнерный стенд (`make stand`, входит в `make smoke`) запускается как отдельный проект `telegram-max-bridge-stand` с образом `telegram-max-bridge:stand`, синтетическими токенами и mock API Telegram/MAX во внутренней сети без выхода наружу. Он проверяет текст, фото и ответы в обе стороны, дедупликацию повторных событий, сохранность очереди и связей ответов при пересоздании, `down`/`up` и `update`, SIGTERM во время подготовки фото и публикации, отсутствие автоповтора `uncertain`, healthcheck при зависшем процессе (включая код `make health`) и отказ сборки при `update`. Сценарии D2 проверяют временные отказы API обеих платформ:

- 3× 503 опроса Telegram и отказ соединений MAX с последующим восстановлением;
- `429` с `Retry-After` в секундах и в формате HTTP-date;
- сбои скачивания фото и `attachment.not.ready`;
- 5xx и обрыв ответа после возможной публикации, в том числе после пересоздания контейнера;
- сохранение назначенного срока повтора при пересоздании контейнера.

Сценарии D3 останавливают процесс в точной точке (SIGSTOP из обёртки стенда `stand_bridge.py`, включается только для одного контейнера), проверяют SQLite и mock, затем завершают контейнер SIGKILL и запускают новый:

- внутри транзакции приёма пакета (несколько сообщений, длинное из двух частей, карантин): курсор не сдвинут, повтор пакета принимается один раз;
- во время подготовки фото в обе стороны; после фиксации `sending` до POST; после принятия публикации API до записи результата; сразу после фиксации `sent`; между частями длинного сообщения;
- повтор входных событий после аварии, эхо собственных ботов, другой бот и два одинаковых текста;
- неизменность данных, схемы и состояний доставки (логический снимок SQLite) при `status`/`health`/`queue list`/`quarantine list`, подтверждение `uncertain` с восстановлением связи ответа и отказ второго экземпляра на том же volume.

Имя проекта стенда — `<PROJECT>-stand` (`STAND_PROJECT=...` выбирает другое). Стенд отказывается работать, ничего не останавливая и не удаляя, если это имя совпадает с `PROJECT` или `telegram-max-bridge`, если в проекте есть контейнеры или volume без метки `telegram-max-bridge.stand=1` либо если Docker не смог перечислить ресурсы для проверки. После проверки стенд удаляет только свои контейнеры и volume.

Текущая версия в контейнере использует polling одной пары групп. D5 добавляет очистку и контроль хранилища. Каналы, несколько связок, webhook, резервное копирование/восстановление и внешняя доставка оповещений требуют дальнейшей работы.

Проверки остановки D5 дополнительно посылают SIGTERM внутри транзакции приёма Telegram и MAX: курсор, задачи частей и карантин сохраняются атомарно; повтор событий после запуска не создаёт дублей. Отдельный сценарий заполняет только ограниченный 128-МиБ том стенда перед финальной записью состояния: проверяются настоящий `SQLITE_FULL`, код 1, отсутствие ложного успешного завершения, сохранность очереди и восстановление после освобождения места.

### Контроль хранилища (D5.1)

`make status` и `make cli ARGS='health --json'` показывают размеры двух SQLite, их WAL/SHM, alerts и свободное место volume. Предупреждение находится в `warnings`; критический уровень или ошибка измерения — в `issues`, `health` возвращает код 1. При критическом уровне приём новых пакетов ждёт освобождения места; heartbeat и обработка уже принятой очереди продолжаются. Размеры — диагностические пороги, не квота SQLite и не оценка всего расхода Docker.

`/tmp` каждого контейнера ограничен 64 МиБ. Monitor ротирует `alerts.jsonl`: по умолчанию 10 МиБ на файл, текущий + 4 архива, история не старше 90 дней. Настройки и действия — в [OPERATIONS](02-messenger-sync/poc/OPERATIONS.md#контроль-хранилища-d51); переменные перечислены в `.env.example`. Make загружает этот файл для интерполяции Compose, окружение процесса имеет приоритет. Для применения настроек выполнить `make update`. В smoke давление проверяется настоящим файлом 64 МиБ на отдельном ограниченном 128-МиБ файловом томе; обычные volume и их сохранность проверяются прежними D1–D4. Очистка задач/истории SQLite описана ниже; схема базы остаётся 3.

### Очистка SQLite (D5.2)

Существующие владельцы баз автоматически обслуживают их небольшими пакетами: по умолчанию каждые 60 с, до 100 просмотренных строк каждой таблицы и 50 мс SQL на пакет. Через 30 дней после завершения всех частей сообщения содержимое заменяется отметкой очистки; ID, состояния, ready и соответствия ответов сохраняются. Нерешённые задачи и открытый карантин не очищаются. Закрытая история обслуживается через 90 дней; невыданный outbox и текущие проблемы сохраняются. Срок означает минимальный возраст: обработка выполняется при очередном обходе пакетов. У старых выданных оповещений без времени ACK 90 дней отсчитываются от первого обслуживания.

`make maintenance` показывает только количества в следующем пакете и объём страниц; ничего не изменяет. Для применения остановить оба сервиса через `make down`, затем выполнить `make maintenance APPLY=1` и `make up`. Автоматическая очистка продолжит обход с сохранённых позиций. `make compact` выполняется так же при остановленных сервисах: это отдельный явный VACUUM, требует резерва не менее двойного суммарного размера файлов БД плюс критический резерв места. Он не запускается автоматически. Освобождённые страницы могут переиспользоваться, но очистка сама по себе не гарантирует уменьшения файлов или устранения всей фрагментации.

`status`/`health` показывают последний результат обслуживания и число свободных страниц. `queue list/show` и `quarantine list/show` показывают `content_cleared`. Настройки, ограничения и порядок применения — в [OPERATIONS](02-messenger-sync/poc/OPERATIONS.md#очистка-sqlite-d52). Реальные сообщения в Telegram/MAX не удаляются. Миграции данных нет, добавляется совместимый частичный индекс нерешённых задач; уже очищенное содержимое при откате кода не восстанавливается.

Штатные `make test` и `make smoke` проверяют также совместимость с физической базой v3 из синтетического SQL-снимка старой версии: сохранность строк, ID, привязки, очереди и reply при добавлении индекса, последующую очистку и дедупликацию. Smoke повторяет проверки на собственном постоянном volume. История monitor проверяется через перезапуск между двумя наблюдениями восстановления, ошибку вывода до ACK и границу 90 дней после успешной выдачи; записи, связанные с неподтверждённым восстановлением, защищены. Старый код, Git и сеть для этих тестов не нужны.

`make test` включает парный сценарий 60 циклов «приём → доставка → старение → очистка» с включённым удалением содержимого и при `RETENTION_CONTENT_ENABLED=0`. `make smoke` повторяет его в собственных временных каталогах постоянного volume стенда. API в этом сценарии имитируется; используются настоящие обработчики моста, файлы SQLite/WAL, ротация alerts и явный compact. Измерения делаются на каждом цикле, в выводе остаются контрольные точки и максимумы. Сохранение ID, старых reply, нерешённой очереди и невыданных оповещений проверяется отдельно от размера файлов. Протокол — в [плане D5.2](02-messenger-sync/poc/SERVER-DEPLOYMENT-PLAN.md#d52-безопасная-очистка-sqlite).

## Локальный запуск и проверки без Docker

Нужны Linux или macOS, Python 3.11+ и `uv`. Команды ниже выполняются из корня репозитория. Зависимость `aiohttp` зафиксирована в `uv.lock`.

```sh
uv sync --locked
.venv/bin/python -m unittest discover -s 02-messenger-sync/poc -p 'test_*.py' -v
.venv/bin/python 02-messenger-sync/poc/smoke_p0.py
.venv/bin/python 02-messenger-sync/poc/smoke_async.py
```

Тесты используют временные базы и локальные HTTP-стенды, не обращаются к рабочим ботам и не изменяют рабочую очередь. Для HTTP-тестов нужен локальный listener.

Эта инструкция запуска относится к **текущей одной паре групп**; подключение каналов по ней ещё недоступно. Создать `02-messenger-sync/.env` по [образцу](02-messenger-sync/.env.example), задать права `0600`, заполнить токены **своих тестовых ботов**, их имена и при необходимости `MAX_CA_FILE`. Добавить ботов в две закрытые тестовые группы: Telegram должен видеть сообщения участников (отключённый Privacy Mode или роль администратора), MAX — иметь `read_all_messages` и возможность отправки. Файлы `.env` и `.state/` исключены из Git; после клонирования их нужно подготовить отдельно.

```sh
.venv/bin/python 02-messenger-sync/poc/bridge.py doctor
.venv/bin/python 02-messenger-sync/poc/bridge.py discover --seconds 90
.venv/bin/python 02-messenger-sync/poc/bridge.py bind
.venv/bin/python 02-messenger-sync/poc/bridge.py doctor
.venv/bin/python 02-messenger-sync/poc/bridge.py run
```

`doctor` проверяет ботов, группы, права и отсутствие webhook-подписок. `discover` показывает одноразовую фразу: отправить её обычным участником в **каждую тестовую группу** во время работы команды. Затем `bind` записывает найденные ID в `.env`. `discover` подтверждает полученные обновления ботов, поэтому его нельзя запускать на рабочих ботах. `run` останавливается через Ctrl+C; база и очередь остаются в `02-messenger-sync/.state/`. С одними ботами одновременно должен работать только один экземпляр.

Состояние и действия при сбоях описаны в [инструкции оператора](02-messenger-sync/poc/OPERATIONS.md). Токены и данные переписки не включать в Git, логи или заявки на поддержку.
